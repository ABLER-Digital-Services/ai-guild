# 基盤概要設計_可用性編スキル

システムを構成する各層（コンピュート・データベース・キャッシュ・ストレージ・ネットワーク）の冗長化・多重化方法と、
フェイルオーバー・スケーリング・ヘルスチェック・計画停止の各設計を定義するドキュメントを作成・更新する。
可用性目標（SLA・稼働率）から逆算してSPOF（単一障害点）を排除し、
RTO/RPO 目標と整合したシステム構成を規定する。

## When to Use This Skill

- 「可用性設計書を作って」「基盤概要設計_可用性編を作って」と言われたとき
- 「冗長化設計を書いて」「多重化設計を整理して」と言われたとき
- 「SLA を定義して」「稼働率目標を決めて」「可用性目標を設定して」と言われたとき
- 「フェイルオーバー設計を書いて」「自動フェイルオーバーを設計して」と言われたとき
- 「マルチAZ 設計を書いて」「AZ 障害対策を設計して」と言われたとき
- 「Auto Scaling 設計を書いて」「スケーリングポリシーを定義して」と言われたとき
- 「ゼロダウンタイムデプロイを設計して」「メンテナンスウィンドウを定義して」と言われたとき
- 「SPOF を洗い出して」「単一障害点を排除して」と言われたとき
- 既存の可用性設計書をレビュー・更新するとき

## MECE 章構成の設計思想

可用性設計を「なぜ（目標）→ 何が（対象）→ どう（方式）→ 検証」の流れで分解することで MECE を実現する。

```
1. 設計方針・可用性目標      ← なぜこの設計か、稼働率目標・SLA・設計原則（Why）
2. SPOF 分析・冗長化対象一覧  ← 何が単一障害点か、どこを多重化するか（What/棚卸し）
3. 層別冗長化・多重化設計    ← 各層でどう冗長化するか（How/コンピュート/DB/NW等）
4. フェイルオーバー設計      ← 障害発生時に自動でどう切り替わるか（Failover/切替設計）
5. スケーリング設計          ← 負荷増加時にどう自動拡張するか（Scaling/Auto Scaling）
6. ヘルスチェック設計        ← 生死をどう検知するか（Health/監視エンドポイント）
7. 計画停止・メンテナンス設計 ← 計画的なダウンタイムをどう最小化するか（Maintenance）
8. 可用性検証・運用設計      ← 設計どおりに動くか定期的にどう確認するか（Verification）
```

**MECE の根拠:**
- 2（何を多重化するか）≠ 3（どう多重化するか）: SPOF 棚卸しと多重化方式設計は独立した作業
- 3（冗長化方式）≠ 4（フェイルオーバー）: 冗長構成の「構造」と「切替動作」は別の関心事
- 4（フェイルオーバー）≠ 5（スケーリング）: フェイルオーバーは「障害時の切替」、スケーリングは「負荷変化への対応」
- 5（スケーリング）≠ 6（ヘルスチェック）: スケーリングは「追加・削除の条件」、ヘルスチェックは「生死の検知方法」
- 6（ヘルスチェック）≠ 7（計画停止）: ヘルスチェックは「常時監視」、計画停止は「意図的なダウンタイム管理」
- 7（計画停止）≠ 8（検証）: 計画停止は「手順定義」、検証は「フェイルオーバーテスト・カオスエンジニアリング等の定期確認」

## 作成ワークフロー

### Step 1: テンプレートをコピーして成果物を作成

例として、`templates/基盤概要設計_可用性編_template.md` を
`docs/01_要件定義/02_非機能/12_可用性/基盤概要設計_可用性編.md` にコピーして作業を開始する。

既存ファイルがある場合は上書きせず、差分を確認してから追記・修正する。

### Step 2: 関連ドキュメントの参照

以下のドキュメントを事前に参照し、設計の一貫性を確保する：

| ドキュメント | 参照目的 |
|---|---|
| `01_非機能要求グレード.md` | 可用性目標（稼働率・RTO/RPO）・障害許容方針・SLA 要件の確認 |
| `基盤概要設計_クラウドサービス編.md` | 利用 AWS サービス・アカウント設計・リージョン構成の確認 |
| `基盤概要設計_サーバ編.md` | EC2 インスタンス構成・台数・配置 AZ の確認 |
| `基盤概要設計_ネットワーク編.md` | VPC/サブネット構成・ALB/NLB 配置・マルチ AZ 設計の確認 |
| `基盤概要設計_データベース編.md` | RDS Multi-AZ・フェイルオーバー設定・Read Replica 構成の確認 |
| `基盤概要設計_ストレージ編.md` | EBS/S3 の冗長性・耐久性設計の確認 |
| `基盤概要設計_バックアップ・リカバリ編.md` | RTO/RPO 目標・DR 設計との整合確認 |
| `基盤概要設計_監視編.md` | 障害検知・ヘルスチェック・アラート設計との整合確認 |

### Step 3: ユーザーへのヒアリング

以下の観点でシステムの要件を確認する：

**可用性目標の確認**
- SLA/稼働率目標（例: 99.9% → 月間ダウンタイム約 43 分）
- 計画停止の扱い（SLA 算出から除外するか否か）
- RTO（目標復旧時間）・RPO（目標復旧時点）のバックアップ・リカバリ編との整合
- 対象とする障害クラス（AZ 障害 / リージョン障害 / インスタンス障害 等）

**冗長化・多重化要件の確認**
- 必ず Multi-AZ にすべき tier（Web 層 / AP 層 / DB 層 等）
- コスト上の制約でシングル AZ を許容する tier・コンポーネントの有無
- マネージドサービス利用の場合、ベンダーが提供する冗長化の範囲と制約（Multi-AZ 有無・フェイルオーバー設定権限等）

**フェイルオーバー要件の確認**
- DB フェイルオーバー時の許容時間（RDS Multi-AZ：通常 30〜120 秒）
- ALB ヘルスチェック失敗時の振り分け除外までの許容時間
- DNS フェイルオーバーの要否（Route 53 ヘルスチェック + フェイルオーバールーティング）
- アプリケーション側のリトライ設計有無（DB フェイルオーバー時の接続断への対応）

**スケーリング要件の確認**
- スケールアウトが必要な tier（Web 層 / AP 層 等）
- スケーリングのトリガー指標（CPU 使用率 / リクエスト数 / メモリ使用率 等）
- 最小・最大・希望インスタンス数の目安
- スパイク時の事前スケーリング（予測スケーリング）の必要性

**計画停止・メンテナンス要件の確認**
- メンテナンス時のダウンタイム許容有無（ゼロダウンタイムデプロイの要否）
- デプロイ方式（ブルーグリーン / ローリングアップデート / インプレース）
- AWS マネージドサービスのメンテナンスウィンドウ設定の制約
- 深夜・休日メンテナンスの実施可否

**検証・テスト要件の確認**
- フェイルオーバーテストの実施有無・頻度
- カオスエンジニアリング（AWS Fault Injection Simulator 等）の適用有無
- 定期的な可用性レビューの実施頻度

### Step 4: 各セクションの記述

テンプレートのプレースホルダーをヒアリング結果に基づいて埋める。

記述の基本スタイル:
- 冗長化対象は「構成要素ごと」に多重化方式・AZ 配置・フェイルオーバー有無を表形式で整理する
- 稼働率目標は数値で明示し、計算根拠（例: ダウンタイム換算）を記載する
- SPOF 一覧では「意図的に冗長化しない理由」も記載してリスクを可視化する
- 未確定・要調査項目は `> **TODO:**` でマーク

記述例:

```markdown
### RDS（PostgreSQL）

| 項目 | 内容 |
|---|---|
| 冗長化方式 | RDS Multi-AZ（同期レプリケーション） |
| スタンバイ配置 | ap-northeast-1a（Primary）/ ap-northeast-1c（Standby） |
| フェイルオーバー | 自動（Primary 障害検知後 30〜120 秒で Standby に昇格）|
| フェイルオーバー検知 | AWS 内部ヘルスチェック（お客様設定不要）|
| リードレプリカ | なし（読取性能要件なし）|
| 管理責任 | Multi-AZ 有効化設定: お客様管理 |
```

### Step 5: レビューチェック

- [ ] 可用性目標（稼働率・RTO/RPO）が数値で明示されているか
- [ ] すべてのシステム構成要素が SPOF 分析一覧に列挙されているか
- [ ] SPOF として残る要素に対してリスクと対応方針が記載されているか
- [ ] 各層（コンピュート/DB/キャッシュ/ストレージ/ネットワーク/DNS）の冗長化方式が定義されているか
- [ ] フェイルオーバー切替時間が RTO 目標と整合しているか
- [ ] Auto Scaling の最小台数が無冗長（1台）になっていないか
- [ ] ヘルスチェックの設定（間隔・閾値・パス）が定義されているか
- [ ] 計画停止手順とダウンタイム目標が定義されているか
- [ ] 非機能要求グレードの可用性要件と整合しているか
- [ ] バックアップ・リカバリ編の RTO/RPO と矛盾していないか
- [ ] フェイルオーバーテストの計画が記述されているか
- [ ] マネージドサービスを利用する場合、ベンダーの制約（Multi-AZ 有無・フェイルオーバー設定権限等）と整合しているか

## テンプレートの構成

テンプレート（`templates/基盤概要設計_可用性編_template.md`）は以下のセクションで構成される：

| # | セクション | 主な内容 |
|---|---|---|
| 1 | 設計方針・可用性目標 | 稼働率目標・SLA 計算・設計原則・障害クラス定義 |
| 2 | SPOF 分析・冗長化対象一覧 | 全構成要素の SPOF 有無・冗長化方式・冗長化しない理由 |
| 3 | 層別冗長化・多重化設計 | コンピュート／DB／キャッシュ／ストレージ／ネットワーク／DNS 各層の設計 |
| 4 | フェイルオーバー設計 | 自動フェイルオーバー設定・切替時間・アプリ側対応 |
| 5 | スケーリング設計 | Auto Scaling グループ設定・スケーリングポリシー・予測スケーリング |
| 6 | ヘルスチェック設計 | ALB ヘルスチェック・Route 53 ヘルスチェック・アプリヘルスチェックエンドポイント |
| 7 | 計画停止・メンテナンス設計 | デプロイ方式・メンテナンスウィンドウ・ゼロダウンタイム方針 |
| 8 | 可用性検証・運用設計 | フェイルオーバーテスト計画・カオスエンジニアリング方針・定期レビュー |
