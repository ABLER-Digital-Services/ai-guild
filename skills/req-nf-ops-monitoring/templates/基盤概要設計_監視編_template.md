本書は「＜システム名＞」の監視基盤設計を定義する。
システムを構成する AWS サービス・アプリケーション・ネットワーク・セキュリティを対象に、監視種別ごとの監視観点・監視間隔・閾値・通知条件・通知方法・エスカレーションフローを規定し、障害の早期検知とサービス継続を実現する。

## 前提条件

| 項目 | 内容 |
|---|---|
| 基盤 | ＜クラウドプラットフォーム名・プラン名＞ |
| クラウドリージョン | ＜AWS リージョン（例: ap-northeast-1 東京）＞ |
| 主監視ツール | ＜CloudWatch / Datadog / Mackerel / Zabbix / Prometheus + Grafana 等＞ |
| インフラ管理責任 | ＜インフラ監視はベンダー管理 / お客様管理等＞ |
| SLA・稼働率目標 | ＜例: 99.9%（月間ダウンタイム許容 43分以内）＞ |
| 参照ドキュメント | ＜非機能要求グレード / RFP 等＞ |

### 管理責任区分

| 区分 | 意味 |
|---|---|
| **基盤管理** | クラウドプラットフォーム提供事業者（ベンダー）が管理・設定する |
| **お客様管理** | お客様（開発者・運用担当者）が設定・運用する |
| **お客様申請** | プラットフォーム事業者へ申請することで設定できる |

### 監視設計における基本方針

- **全対象カバー原則**: システムを構成するすべてのコンポーネントを監視種別一覧で棚卸しし、監視漏れを残さない
- **閾値の根拠明示**: 各監視項目の閾値は SLA 逆算・ベストプラクティス・過去実績のいずれかを根拠として明記する
- **アラート疲れ防止**: 閾値は「即時対応が必要なイベント」に絞り、過検知・誤検知を最小化する
- **エスカレーション明確化**: 通知先・エスカレーションルートを時間帯・優先度別に定義し、対応漏れを防ぐ
- **ダッシュボードによる可視化**: 主要 KPI をダッシュボードで常時可視化し、障害予兆の早期把握を可能にする

## 2. 死活監視設計

### 2.1. サーバ死活監視（EC2）

**目的**: EC2 インスタンスの稼働状態を確認し、インスタンス障害を即時検知する。

| 監視項目 | 監視ツール | 監視間隔 | 通知条件 | 通知先 | 管理責任 |
|---|---|---|---|---|---|
| EC2 StatusCheckFailed（システムステータス） | CloudWatch | 1分 | 1分継続で ≥ 1 | SNS → PagerDuty / メール | **お客様管理** |
| EC2 StatusCheckFailed（インスタンスステータス） | CloudWatch | 1分 | 1分継続で ≥ 1 | SNS → PagerDuty / メール | **お客様管理** |

> **TODO:** Auto Scaling を利用している場合は、インスタンス起動・終了イベントも通知対象とするか検討すること。

### 2.2. エンドポイント死活監視（外形監視）

**目的**: 外部からシステムの公開 URL に定期的にアクセスし、エンドユーザー視点での可用性を確認する。

| 監視対象 URL | プロトコル | 監視間隔 | 正常条件 | 通知条件 | 監視ツール | 管理責任 |
|---|---|---|---|---|---|---|
| `＜公開 URL（例: https://example.com/health）＞` | HTTPS | 1分 | HTTP 200 かつ レスポンスタイム < 3秒 | HTTP 200 以外 または タイムアウト | CloudWatch Synthetics | **お客様管理** |

> **TODO:** 監視対象 URL・正常判定条件（レスポンスボディの特定文字列チェック等）を本システムに合わせて設定すること。

### 2.3. ロードバランサ死活監視（ALB）

**目的**: ALB 配下の正常なターゲットが 0 台になる状態（全インスタンス異常）を検知する。

| 監視項目 | 監視ツール | 監視間隔 | 通知条件 | 通知先 | 管理責任 |
|---|---|---|---|---|---|
| HealthyHostCount | CloudWatch | 1分 | < 1 | SNS → PagerDuty / メール | **お客様管理** |
| UnHealthyHostCount | CloudWatch | 1分 | ≥ 1 が 5分継続 | SNS → Slack #監視 | **お客様管理** |

### 2.4. バッチ処理・Lambda 死活監視

**目的**: 非同期で実行されるバッチ・Lambda の実行失敗・タイムアウトを検知する。

| 監視対象 | 監視項目 | 監視ツール | 通知条件 | 通知先 | 管理責任 |
|---|---|---|---|---|---|
| Lambda 関数 | Errors（実行エラー数） | CloudWatch | ≥ 1 | SNS → Slack #監視 | **お客様管理** |
| Lambda 関数 | Throttles（スロットリング数） | CloudWatch | ≥ 1 が 5分継続 | SNS → Slack #監視 | **お客様管理** |
| ECS タスク / バッチジョブ | タスク停止イベント（STOPPED） | EventBridge | 異常終了（exitCode ≠ 0） | SNS → メール | **お客様管理** |
| スケジュールバッチ | 実行完了通知なし（タイムアウト） | CloudWatch Alarms または EventBridge | 規定時間内に完了通知がない場合 | SNS → メール | **お客様管理** |

## 3. リソース監視設計

### 3.1. APサーバ（EC2）リソース監視

**目的**: APサーバのリソース逼迫を早期に検知し、スケールアウト・チューニングの判断材料とする。

| 監視項目 | 監視ツール | 監視間隔 | 警告閾値 | 危険閾値 | 持続時間 | 通知先 | 管理責任 |
|---|---|---|---|---|---|---|---|
| CPU 使用率 | CloudWatch（EC2 標準） | 1分 | ≥ 70% | ≥ 90% | 5分継続 | 警告: Slack、危険: PagerDuty + Slack | **お客様管理** |
| メモリ使用率 | CloudWatch Agent（カスタム） | 1分 | ≥ 70% | ≥ 90% | 5分継続 | 警告: Slack、危険: PagerDuty + Slack | **お客様管理** |
| ディスク使用率（/） | CloudWatch Agent（カスタム） | 5分 | ≥ 70% | ≥ 90% | 5分継続 | 警告: Slack、危険: PagerDuty + Slack | **お客様管理** |
| ディスク使用率（/var/log 等） | CloudWatch Agent（カスタム） | 5分 | ≥ 70% | ≥ 85% | 5分継続 | 警告: Slack | **お客様管理** |
| ネットワーク IN/OUT（バイト数） | CloudWatch（EC2 標準） | 5分 | ＜要定義＞ | ＜要定義＞ | - | Slack | **お客様管理** |

> **TODO:** CloudWatch Agent のインストール・設定（`/etc/amazon/amazon-cloudwatch-agent.json`）により、メモリ・ディスクは標準では取得されないため、カスタムメトリクスとして追加する必要がある。ベンダー  等のマネージドサービスを利用している場合、エージェントのインストール可否をベンダーへ確認すること。

### 3.2. RDS / Aurora リソース監視

**目的**: DB の性能劣化・容量不足・接続枯渇を早期検知する。

| 監視項目 | 監視ツール | 監視間隔 | 警告閾値 | 危険閾値 | 持続時間 | 通知先 | 管理責任 |
|---|---|---|---|---|---|---|---|
| CPU 使用率 | CloudWatch（RDS 標準） | 1分 | ≥ 70% | ≥ 90% | 5分継続 | 警告: Slack、危険: PagerDuty + Slack | **お客様管理** |
| フリーストレージ容量 | CloudWatch（RDS 標準） | 5分 | < 10 GB | < 5 GB | - | 警告: Slack、危険: PagerDuty + メール | **お客様管理** |
| DB 接続数（DatabaseConnections） | CloudWatch（RDS 標準） | 1分 | 最大接続数の 70% | 最大接続数の 90% | 5分継続 | 警告: Slack、危険: PagerDuty + Slack | **お客様管理** |
| フリーメモリ（FreeableMemory） | CloudWatch（RDS 標準） | 5分 | < 1 GB | < 512 MB | - | 警告: Slack、危険: PagerDuty | **お客様管理** |
| レプリカラグ（ReplicaLag） | CloudWatch（RDS 標準） | 1分 | ≥ 30秒 | ≥ 60秒 | - | 警告: Slack | **お客様管理** |
| RDS イベント（フェイルオーバー・再起動等） | RDS イベント通知（SNS） | リアルタイム | イベント発生時 | - | - | SNS → メール / Slack | **お客様管理** |

> **TODO:** Aurora の場合は `ServerlessDatabaseCapacity`（ACU 使用量）・`BufferCacheHitRatio` 等も監視対象とすること。最大接続数はインスタンスタイプとエンジンによって異なるため、`max_connections` パラメータを確認の上、閾値を設定すること。

## 4. アプリケーション監視設計

**目的**: エンドユーザーが実感するシステムの品質（レスポンス・エラー）を継続的に計測し、劣化を早期検知する。

### 4.1. HTTP エラー率・レスポンスタイム監視

| 監視項目 | 監視ツール | 監視間隔 | 警告閾値 | 危険閾値 | 持続時間 | 通知先 | 管理責任 |
|---|---|---|---|---|---|---|---|
| ALB 5xx エラー率（`HTTPCode_ELB_5XX_Count`）| CloudWatch（ALB 標準） | 1分 | ≥ 1% | ≥ 5% | 3分継続 | 警告: Slack、危険: PagerDuty + Slack | **お客様管理** |
| ALB 4xx エラー率（`HTTPCode_Target_4XX_Count`） | CloudWatch（ALB 標準） | 1分 | ≥ 5% | - | 5分継続 | Slack | **お客様管理** |
| ALB レスポンスタイム P95（`TargetResponseTime`） | CloudWatch（ALB 標準） | 1分 | ≥ 2秒 | ≥ 5秒 | 3分継続 | 警告: Slack、危険: PagerDuty | **お客様管理** |
| CloudFront 5xx エラー率 | CloudWatch（CloudFront 標準） | 1分 | ≥ 1% | ≥ 5% | 3分継続 | 警告: Slack、危険: PagerDuty | **お客様管理** |

### 4.2. 外形監視（Synthetic Monitoring）

**目的**: 定期的に外部から公開 URL にアクセスし、実際のユーザー体験に近い形での可用性・レスポンスを確認する。

| 監視対象 | 監視 URL | 確認内容 | 監視間隔 | 監視箇所 | 通知条件 |
|---|---|---|---|---|---|
| トップページ | `＜https://example.com/＞` | HTTP 200 / レスポンスタイム < 3秒 | 1分 | ap-northeast-1 + ap-southeast-1（複数拠点推奨） | 失敗 2回連続 |
| ヘルスチェック API | `＜https://example.com/health＞` | HTTP 200 / JSON `{"status":"ok"}` 含む | 1分 | ap-northeast-1 | 失敗 1回 |
| ログイン画面 | `＜https://example.com/login＞` | HTTP 200 | 5分 | ap-northeast-1 | 失敗 2回連続 |

### 4.3. ビジネス KPI 監視

**目的**: アプリケーション固有のビジネス指標（処理件数・申請数等）を監視し、業務上の異常を検知する。

|---|---|---|---|---|

## 6. セキュリティ監視設計

**目的**: 不正アクセス・設定ミス・脅威を自動検知し、インシデント対応を迅速化する。

### 6.1. Amazon GuardDuty

**概要**: AWS アカウント・VPC フローログ・CloudTrail を分析し、脅威を自動検知する。

| 項目 | 設定値 | 管理責任 |
|---|---|---|
| 有効化対象 | すべての AWS リージョン | **お客様管理** |
| Findings の通知 | EventBridge ルール → SNS → メール / PagerDuty | **お客様管理** |
| 通知対象 Severity | HIGH（7.0〜） は即時通知 / MEDIUM（4.0〜） は日次サマリー | **お客様管理** |
| Findings のアーカイブ先 | S3 バケット（ログバケット）+ Security Hub | **お客様管理** |

> **TODO:** ベンダー  等のマネージドサービスを利用している場合、GuardDuty の有効化可否をベンダーサポートへ確認すること。

### 6.2. AWS WAF 監視

**概要**: Web アプリケーションへの不正リクエストのブロック状況を監視する。

| 監視項目 | 監視ツール | 監視間隔 | 通知条件 | 通知先 | 管理責任 |
|---|---|---|---|---|---|
| ブロックリクエスト数（`BlockedRequests`） | CloudWatch | 5分 | ≥ 100件/分 が 5分継続 | Slack | **お客様管理** |
| 特定ルール一致数（カスタムルール Alarm） | CloudWatch | 5分 | ＜要定義＞ | Slack | **お客様管理** |

> **TODO:** WAF を利用しない場合、本セクションは削除すること。

### 6.3. IAM・CloudTrail セキュリティ監視

**目的**: IAM のルートアカウント利用・大量 API エラー等、不審な AWS 操作を検知する。

| 監視項目 | 検知方法 | 通知条件 | 通知先 | 管理責任 |
|---|---|---|---|---|
| ルートアカウントログイン | CloudTrail → CW Logs メトリクスフィルター | 1件以上 | SNS → PagerDuty + メール | **お客様管理** |
| IAM ポリシー変更・削除 | CloudTrail → CW Logs メトリクスフィルター | 1件以上 | SNS → メール | **お客様管理** |
| AWS コンソールログイン失敗連続 | CloudTrail → CW Logs メトリクスフィルター | 5分以内に 5回以上 | SNS → Slack | **お客様管理** |
| セキュリティグループ変更 | CloudTrail → CW Logs メトリクスフィルター | 1件以上 | SNS → Slack | **お客様管理** |

### 6.4. AWS Security Hub（オプション）

**目的**: GuardDuty・Macie・Inspector 等の各セキュリティサービスの検知結果を一元管理・可視化する。

## 7. ログ監視設計

**目的**: アプリケーション・インフラのログから特定のパターン（エラー・異常・不正）を検知し、自動アラートを発火させる。

> ログの保管・分析設計は `基盤概要設計_ログ管理編.md` を参照すること。本セクションは「ログからアラートを発火させるためのルール定義」に特化する。

### 7.1. CloudWatch Logs メトリクスフィルター定義

| # | フィルター名 | 対象ロググループ | フィルターパターン | 閾値 | 通知先 |
|---|---|---|---|---|---|
| F-01 | AppErrorCount | `/app/application` | `[ERROR]` | ≥ 10件/分 | Slack #監視 |
| F-02 | LoginFailureCount | `/app/access` | `"LOGIN_FAILED"` | ≥ 5件/5分 | Slack #セキュリティ |
| F-03 | DBSlowQueryCount | `/aws/rds/cluster/<cluster-name>/slowquery` | `Query_time` | ≥ 1件/分 が 5分継続 | Slack #監視 |
| F-04 | OutOfMemoryError | `/app/application` | `"OutOfMemoryError"` | ≥ 1件 | PagerDuty + Slack |
| F-05 | RootLoginDetect | `CloudTrail/DefaultLogGroup` | `"eventName":"ConsoleLogin"` かつ `"userIdentity.type":"Root"` | ≥ 1件 | PagerDuty + メール |

> **TODO:** アプリケーション固有のエラーメッセージ・ログフォーマットに合わせてフィルターパターンを調整すること。ログが JSON 形式の場合は JSON パターンマッチングを使用すること（例: `{ $.level = "ERROR" }`）。

## 8. 通知・エスカレーション設計

### 8.1. 通知チャネル定義

| チャネル | 用途 | 対象優先度 | 受信者 |
|---|---|---|---|
| PagerDuty / OpsGenie | 緊急・即時対応が必要なアラート | P1（Critical） | オンコール担当者（24時間365日） |
| Slack `#監視-alert` | 一般的な警告・情報通知 | P2（Warning） | 開発チーム・運用チーム |
| Slack `#監視-critical` | 危険レベルのアラート | P1（Critical） | 開発チーム・運用チーム・マネージャー |
| メール | 変更通知・日次サマリー・PagerDuty エスカレーション | P1（Critical）/ P3（Info） | 運用担当者・管理者 |
| SMS | 重大障害時のフォールバック | P1（Critical）緊急時のみ | オンコール担当者 |

### 8.2. アラート優先度定義

| 優先度 | 定義 | 例 | 対応期限（目安） |
|---|---|---|---|
| **P1（Critical）** | サービス停止・データ損失・セキュリティインシデント | サーバ停止・DB接続不能・GuardDuty HIGH | 15分以内に初動対応 |
| **P2（Warning）** | 性能劣化・閾値超過（即時停止は伴わない） | CPU 90%・ディスク残量少・5xx エラー率上昇 | 1時間以内に確認 |
| **P3（Info）** | 情報通知・定期サマリー | RDS フェイルオーバー完了・バッチ正常終了 | 翌営業日中に確認 |

### 8.3. エスカレーションフロー

```
[アラート発火]
    │
    ├─ P1（Critical）
    │       │
    │       ├─ 即時: PagerDuty → オンコール担当者（電話・スマホ通知）
    │       ├─ 15分後未応答: 次の担当者へエスカレーション
    │       └─ 30分後未応答: マネージャー・エスカレーション先へ通知
    │
    └─ P2（Warning）
            │
            ├─ Slack #監視-alert へ通知
            └─ 1時間後未対応: Slack でリマインド通知
```

### 8.4. 時間帯別通知ルール

| 時間帯 | P1（Critical） | P2（Warning） |
|---|---|---|
| 営業時間内（平日 9:00〜18:00） | PagerDuty + Slack + メール | Slack のみ |
| 夜間・休日（上記以外） | PagerDuty（電話通知）+ メール | Slack のみ（翌営業日対応） |

> **TODO:** オンコール体制の有無・担当者ローテーションルールをここに追記すること。PagerDuty を利用しない場合は代替手段（メール + SMS 等）を定義すること。

## 9. ダッシュボード設計

**目的**: システムの稼働状況・主要 KPI を可視化し、障害予兆の早期把握と定期的な運用レビューを可能にする。

### 9.1. 運用ダッシュボード（CloudWatch ダッシュボード）

**対象者**: 運用チーム・開発チーム  
**更新間隔**: リアルタイム（自動更新）

| ウィジェット名 | 表示内容 | グラフ種別 |
|---|---|---|
| サービス稼働状況 | APサーバ / ALB / RDS の死活状態（Green/Red） | アラームステータスウィジェット |
| CPU 使用率（APサーバ） | EC2 CPU 使用率（全インスタンス） | 折れ線グラフ |
| メモリ使用率（APサーバ） | EC2 メモリ使用率（カスタムメトリクス） | 折れ線グラフ |
| DB リソース状況 | RDS CPU / FreeableMemory / 接続数 | 折れ線グラフ（複数） |
| HTTP エラー率 | ALB 5xx / 4xx エラー率 | 折れ線グラフ |
| レスポンスタイム（P95） | ALB TargetResponseTime | 折れ線グラフ |
| リクエスト数 | ALB RequestCount（1分集計） | 棒グラフ |
| アクティブアラーム一覧 | 現在 ALARM 状態の全メトリクス | アラームリスト |

### 9.2. セキュリティダッシュボード（オプション）

**対象者**: セキュリティ担当者・管理者  
**更新間隔**: リアルタイム

| ウィジェット名 | 表示内容 |
|---|---|
| GuardDuty Findings | 過去 7日間の Severity 別件数 |
| WAF ブロック数 | 1時間単位のブロックリクエスト数推移 |
| ログイン失敗数 | 1時間単位の認証失敗ログ数推移 |
| CloudTrail 重要イベント | ルートログイン / IAM 変更イベントの一覧 |

## 10. 監視運用設計

### 10.1. アラート対応フロー

```
[アラート受信]
    │
    ├─ 1. アラート内容・影響範囲の確認（CloudWatch / ダッシュボード参照）
    │
    ├─ 2. 暫定対応の実施（サービス継続を優先）
    │       └─ スケールアップ / プロセス再起動 / フェイルオーバー実施等
    │
    ├─ 3. 根本原因の調査（ログ・メトリクス分析）
    │
    ├─ 4. 恒久対応の実施（コード修正 / 設定変更等）
    │
    └─ 5. 障害報告・再発防止策の記録（インシデントレポート作成）
```

### 10.2. 監視閾値の定期見直し

| 見直し契機 | 頻度 | 実施内容 |
|---|---|---|
| 定期見直し | 月次 | 前月のアラート発火状況を集計し、過検知・未検知の有無を確認 |
| システム変更時 | 変更都度 | スペック変更・機能追加に伴う閾値・監視項目の更新 |
| インシデント後 | 発生都度 | 未検知インシデントを受けての監視ルール追加 |

### 10.3. オンコール体制

| 項目 | 内容 |
|---|---|
| オンコール有無 | ＜あり / なし＞ |
| 対応時間帯 | ＜24時間365日 / 平日夜間のみ 等＞ |
| ローテーション | ＜週次ローテーション / 担当者固定 等＞ |
| 初動対応者 | ＜担当者名またはチーム名＞ |
| エスカレーション先 | ＜担当者名・連絡先＞ |
