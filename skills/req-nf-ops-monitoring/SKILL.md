# 基盤概要設計_監視編スキル

システムを構成する AWS サービス・アプリケーション・ネットワーク・セキュリティについて、
「何を・どのように・どの閾値で・誰に・どう通知するか」を体系的に定義するドキュメントを作成・更新する。
監視種別ごとに観点・間隔・閾値・通知条件・通知方法を明確にし、障害の早期検知とサービス継続を実現する設計を確立する。

## When to Use This Skill

- 「監視設計書を作って」「基盤概要設計_監視編を作って」と言われたとき
- 「監視を整理して」「監視観点を整理して」「監視種別を定義して」と言われたとき
- 「CloudWatch の設計を書いて」「Datadog の設計を書いて」「Mackerel の設計を書いて」と言われたとき
- 「アラートの閾値を定義して」「通知条件を整理して」「通知方法を設計して」と言われたとき
- 「死活監視を設計して」「リソース監視を定義して」「ログ監視を設計して」と言われたとき
- 「エスカレーションフローを定義して」「オンコール体制を整理して」と言われたとき
- 「ダッシュボードを設計して」「監視ダッシュボードを作って」と言われたとき
- 既存の監視設計書をレビュー・更新するとき

## MECE章構成の設計思想

監視設計を「監視の目的・対象・方法・通知・運用」という視点で分解することで MECE を実現する。

```
1. 設計方針・前提条件        ← なぜ監視するか、誰が運用するか（Why/Who）
2. 監視種別一覧              ← 何を監視するか（What/棚卸し）
3. 死活監視設計              ← システムが生きているかどうかの監視（Availability）
4. リソース監視設計          ← CPU・メモリ・ディスク等インフラリソースの監視（Resource）
5. アプリケーション監視設計  ← アプリの正常稼働・レスポンス・エラー率の監視（Application）
6. ネットワーク監視設計      ← 通信経路・帯域・パケットロスの監視（Network）
7. セキュリティ監視設計      ← 不正アクセス・異常検知・脆弱性の監視（Security）
8. ログ監視設計              ← ログから特定パターンを検知するルール定義（Log-based）
9. 通知・エスカレーション設計← 誰に・どの手段で・いつ通知するか（Notification）
10. ダッシュボード設計       ← 監視状態の可視化方法（Dashboard）
11. 監視運用設計             ← 運用フロー・定期見直し・オンコール体制（Ops）
```

**MECEの根拠:**
- 3（生死）≠ 4（リソース）: 死活はエンドポイントの応答有無、リソースは指標値のしきい値監視
- 4（インフラ）≠ 5（アプリ）: インフラはOS/AWSサービスの指標、アプリはビジネスロジック層の指標
- 6（ネットワーク）≠ 3・4: ネットワークはトラフィック/レイテンシ/パケット損失の通信品質
- 7（セキュリティ）: GuardDuty/WAF/IAM Eventなど、他の種別と目的が異なる不正行為の検知
- 8（ログ監視）≠ ログ管理: ログ管理は「保管・分析」、ログ監視は「パターン検知によるアラート発火」
- 9（通知）は 3〜8 と独立: 各監視種別はメトリクス収集の設計、通知はアラート発火後の伝達設計

## 作成ワークフロー

### Step 1: テンプレートをコピーして成果物を作成

例として、`templates/基盤概要設計_監視編_template.md` を
`docs/01_要件定義/02_非機能/10_監視/基盤概要設計_監視編.md` にコピーして作業を開始する。

既存ファイルがある場合は上書きせず、差分を確認してから追記・修正する。

### Step 2: 関連ドキュメントの参照

以下のドキュメントを事前に参照し、設計の一貫性を確保する：

| ドキュメント | 参照目的 |
|---|---|
| `01_非機能要求グレード.md` | 監視間隔・SLA・稼働率要件・障害対応時間（RTO/RPO）の確認 |
| `基盤概要設計_クラウドサービス編.md` | 利用 AWS サービス・監視ツール（CloudWatch / Datadog 等）の確認 |
| `基盤概要設計_サーバ編.md` | 監視対象サーバの構成・OS・MWの確認 |
| `基盤概要設計_ネットワーク編.md` | 監視対象の通信経路・ALB/CloudFront 設計の確認 |
| `基盤概要設計_セキュリティ編.md` | セキュリティ監視要件（GuardDuty / Security Hub / WAF 等）の確認 |
| `基盤概要設計_ログ管理編.md` | ログ監視のアラート要件との整合確認 |
| `基盤概要設計_データベース編.md` | RDS/Aurora 監視指標・スロークエリ閾値等の確認 |

### Step 3: ユーザーへのヒアリング

以下の観点でシステムの特性を確認する：

**監視ツール・基盤の確認**
- 採用する監視ツール（CloudWatch / Datadog / Mackerel / Zabbix / Prometheus + Grafana 等）
- マネージドサービスを利用する場合、監視の管理責任区分（ベンダー管理 / お客様管理）
- 既存の統合監視基盤・SIEM の有無

**監視対象・範囲の確認**
- 監視対象サーバ・コンポーネントの一覧（APサーバ・DBサーバ・LB・CDN 等）
- 外部公開エンドポイントの URL とプロトコル（HTTP/HTTPS/PING 等）
- バッチ処理・Lambda 等の非同期コンポーネントの監視要否

**閾値・通知条件の確認**
- SLA・稼働率目標（例: 99.9%）から逆算した許容ダウンタイム
- 各リソース（CPU・メモリ・ディスク等）の警告・危険しきい値の基準
- 通知の優先度・重要度の分類ルール（P1〜P3 等）

**通知方法・エスカレーションの確認**
- アラート通知先（メール / Slack / PagerDuty / SMS 等）
- 担当者別・時間帯別のエスカレーションルール
- 営業時間外対応の有無（オンコール体制）

**可視化・ダッシュボードの確認**
- ダッシュボードの要否と閲覧対象者（開発チーム / 運用チーム / 経営層等）
- SLA 達成状況の定期レポート要否

### Step 4: 各セクションの記述

テンプレートのプレースホルダーをヒアリング結果に基づいて埋める。

記述の基本スタイル:
- 監視項目ごとに「監視間隔・閾値（警告/危険）・通知条件・通知先」を表形式で整理する
- 閾値の根拠（SLA逆算・過去実績・ベストプラクティス等）を備考欄に記載する
- 未確定・要調査項目は `> **TODO:**` でマーク
- 管理責任区分（基盤管理 / お客様管理）を列として明示する

記述例:

```markdown
### CPU 使用率（APサーバ）

| 監視ツール | 監視間隔 | 警告閾値 | 危険閾値 | 持続時間 | 通知先 |
|---|---|---|---|---|---|
| CloudWatch | 1分 | 70% 以上 | 90% 以上 | 5分継続 | 警告: Slack #監視、危険: PagerDuty + Slack |
```

### Step 5: レビューチェック

- [ ] すべての監視対象（サーバ・ネットワーク・アプリ・セキュリティ・ログ）が種別一覧に列挙されているか
- [ ] 各監視項目に閾値（警告・危険）・監視間隔・通知先が定義されているか
- [ ] 閾値の根拠（SLA・ベストプラクティス等）が明記されているか
- [ ] エスカレーションフローが時間帯別・優先度別に定義されているか
- [ ] 通知チャネル（メール・Slack・PagerDuty 等）とその用途・受信者が明確か
- [ ] ダッシュボードの要件（表示指標・更新間隔・閲覧権限）が定義されているか
- [ ] 監視ツールの管理責任区分が明記されているか
- [ ] 非機能要求グレードの稼働率・障害対応時間要件と整合しているか
- [ ] セキュリティ設計書のセキュリティ監視要件と整合しているか
- [ ] ログ管理設計書のログ監視アラート設計と重複・矛盾がないか

## テンプレートの構成

テンプレート（`templates/基盤概要設計_監視編_template.md`）は以下のセクションで構成される：

| # | セクション | 主な内容 |
|---|---|---|
| 1 | 設計方針・前提条件 | 監視方針・使用ツール・管理責任区分・SLA |
| 2 | 監視種別一覧 | 全監視項目・対象・ツール・担当区分の棚卸し表 |
| 3 | 死活監視設計 | サーバ・エンドポイント・バッチの疎通確認設計 |
| 4 | リソース監視設計 | CPU / メモリ / ディスク / RDS / Lambda 等の指標監視 |
| 5 | アプリケーション監視設計 | HTTPステータス・レスポンスタイム・エラー率・ビジネスKPI |
| 6 | ネットワーク監視設計 | ALB・CloudFront・VPC・DirectConnect 等の通信品質監視 |
| 7 | セキュリティ監視設計 | GuardDuty / Security Hub / WAF / IAM イベント監視 |
| 8 | ログ監視設計 | CloudWatch メトリクスフィルター / アラートパターン定義 |
| 9 | 通知・エスカレーション設計 | 通知チャネル・優先度・時間帯別エスカレーションフロー |
| 10 | ダッシュボード設計 | CloudWatch / Datadog ダッシュボード構成・KPIウィジェット |
| 11 | 監視運用設計 | アラート対応フロー・閾値見直し運用・オンコール体制 |
