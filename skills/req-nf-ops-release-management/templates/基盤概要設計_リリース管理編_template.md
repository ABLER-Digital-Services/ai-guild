# 基盤概要設計_リリース管理編

本書は「＜システム名＞」のリリース管理設計を定義する。
ブランチ戦略・ブランチ保護・PR レビュー・CI/CD パイプライン・バージョン管理・シークレット管理・緊急リリース手順を規定し、
開発チームが安全・迅速・再現可能にソフトウェアをリリースできる基盤を整備する。

## 前提条件

| 項目 | 内容 |
|---|---|
| ソースコード管理 | ＜例: GitHub（github.com/組織名/リポジトリ名）＞ |
| CI/CD プラットフォーム | ＜例: GitHub Actions＞ |
| デプロイ対象基盤 | ＜例: ＜クラウドプラットフォーム・プラン名（本番/開発）＞＞ |
| デプロイ方式制約 | ＜例: APサーバへのデプロイは管理コンソール・デプロイ機能経由（サービス仕様書参照）＞ |
| 参照ドキュメント | ＜サービス仕様書・RFP 等＞ |

### リリース管理における基本方針

- **変更はすべて Pull Request 経由**: 本番相当ブランチ（main / develop）への直接 push を禁止し、変更はすべて PR + レビューを経由させる
- **CI グリーンをマージ条件とする**: テスト・Lint・セキュリティスキャンが全て成功しない限りマージをブロックする
- **シークレットは VCS に含めない**: API キー・パスワード等の機密情報は一切 Git リポジトリにコミットしない
- **デプロイは環境を昇格させる**: 開発 → ステージング → 本番の順に昇格し、各ステップで品質を確認する
- **ロールバック手順を常に準備する**: デプロイ前にバックアップを取得し、問題発生時は速やかに切り戻せる状態を維持する

### 2.2. ブランチ一覧

| ブランチ種別 | 命名規則 | 分岐元 | マージ先 | 残存期間 | 説明 |
|---|---|---|---|---|---|
| 本番ブランチ | `main` | — | — | 永続 | 常に本番デプロイ可能な状態を維持する |
| 開発ブランチ | `develop` | `main` | `main`（PR 経由）| 永続 | ＜Git Flow 採用時のみ。GitHub Flow では省略可＞ |
| 機能開発 | `feature/{issue番号}-{概要（kebab-case）}` | ＜develop / main＞ | ＜develop / main＞（PR 経由）| 機能完成まで（原則 1週間以内）| 新機能の開発 |
| バグ修正 | `fix/{issue番号}-{概要（kebab-case）}` | ＜develop / main＞ | ＜develop / main＞（PR 経由）| 修正完成まで | 通常バグの修正 |
| リリース準備 | `release/{バージョン番号}` | `develop` | `main` ＆ `develop`（PR 経由）| リリース完了まで | ＜Git Flow 採用時のみ＞ リリース前の最終調整 |
| ホットフィックス | `hotfix/{issue番号}-{概要（kebab-case）}` | `main` | `main` ＆ `develop`（PR 経由）| 修正完成まで | 本番緊急修正 |

**命名規則の例:**
- `feature/123-add-application-form`
- `fix/456-fix-login-redirect`
- `hotfix/789-fix-csv-encoding`

### 2.3. マージ方式

| 対象ブランチへのマージ | 推奨マージ方式 | 理由 |
|---|---|---|
| `main` / `develop` へのマージ | **Squash Merge** | コミット履歴をクリーンに保ち、機能単位で1コミットに集約する |
| `release` → `main` | **Merge Commit**（`--no-ff`）| リリースの境界をコミット履歴に残す |
| `hotfix` → `main` | **Merge Commit**（`--no-ff`）| ホットフィックスの記録を履歴に残す |

> **注意:** Squash Merge を使用する場合、各 PR の変更内容が1コミットに集約されるため、PR タイトルがコミットメッセージとなる。PR タイトルは `[種別] 概要` 形式（例: `[feat] 申請フォームの追加`）を必須とする。

## 3. ブランチ保護・アクセス管理

### 3.1. ブランチ保護ルール設定一覧

GitHub リポジトリの `Settings > Branches > Branch protection rules` に以下を設定する。

#### `main` ブランチ

| 設定項目 | 設定値 | 理由 |
|---|---|---|
| Require a pull request before merging | **有効** | 直接 push を禁止し、すべての変更に PR を必須化する |
| Required approvals | **＜例: 1名以上＞** | ＜例: 最低1名のレビュアーの承認を必須とする＞ |
| Dismiss stale pull request approvals when new commits are pushed | **有効** | 新コミット後に古い承認を無効化し、変更後の再レビューを促す |
| Require review from Code Owners | **＜有効 / 無効＞** | ＜CODEOWNERS ファイルを利用する場合は有効にする＞ |
| Require status checks to pass before merging | **有効** | CI（テスト・Lint・セキュリティスキャン）の成功を必須化する |
| Require branches to be up to date before merging | **有効** | base ブランチとの差分解消を必須化し、マージ後の CI 失敗を防ぐ |
| 必須ステータスチェック | ＜例: `lint-and-test` / `sast-scan`＞ | CI ジョブ名を指定する（§5 で定義するジョブ名と一致させること）|
| Do not allow bypassing the above settings | **有効** | 管理者も含め全ユーザーに保護ルールを適用する |
| Allow force pushes | **無効** | コミット履歴の書き換えを禁止する |
| Allow deletions | **無効** | ブランチの誤削除を防ぐ |

#### `develop` ブランチ（Git Flow 採用時）

| 設定項目 | 設定値 |
|---|---|
| Require a pull request before merging | **有効** |
| Required approvals | **＜例: 1名以上＞** |
| Require status checks to pass before merging | **有効** |
| Allow force pushes | **無効** |

`CODEOWNERS` ファイルを利用し、特定のパス・ファイルの変更に対してレビュアーを自動アサインする。

```
/infra/                 @＜インフラ担当チームまたはユーザー名＞
/.github/workflows/     @＜インフラ担当チームまたはユーザー名＞

# セキュリティ関連設定はセキュリティ担当者のレビューを必須とする
/src/main/java/**/auth/ @＜セキュリティ担当者ユーザー名＞
```

## 4. Pull Request・コードレビュー設計

### 4.1. PR テンプレート

`.github/pull_request_template.md` に以下の内容を配置する。

```markdown
## 概要

<!-- この PR で何を変更したかを1〜3文で説明してください -->

## 変更の種別

- [ ] feat（新機能）
- [ ] fix（バグ修正）
- [ ] refactor（機能変更なしのコード改善）
- [ ] docs（ドキュメントのみ）
- [ ] test（テストのみ）
- [ ] chore（ビルド設定・依存関係等）
- [ ] hotfix（本番緊急修正）

## 関連 Issue

Closes #＜Issue番号＞

## 動作確認方法

<!-- レビュアーが動作確認できるよう、確認手順・確認箇所を記載してください -->

1.
2.
3.

## スクリーンショット（UI 変更がある場合）

<!-- 変更前後のスクリーンショットを貼り付けてください -->

## チェックリスト

- [ ] ユニットテストを追加・更新した（または追加不要であることを確認した）
- [ ] ローカルで動作確認した
- [ ] 本 PR のコードに機密情報（API キー・パスワード等）が含まれていないことを確認した
- [ ] ドキュメント（コメント・README 等）を必要に応じて更新した
- [ ] CI の全ジョブがグリーンであることを確認した
```

### 4.2. GitHub Copilot コードレビュー

GitHub Copilot のコードレビュー機能（`github-actions[bot]` または Copilot レビュアー）をリポジトリに有効化し、PR 作成時に自動でコードレビューコメントを生成させる。

| 項目 | 内容 |
|---|---|
| 有効化方法 | GitHub リポジトリ設定 `Settings > Copilot > Copilot code review` を有効化＜または: `.github/workflows/copilot-review.yml` を作成＞ |
| トリガー | PR 作成時・更新時（`pull_request` イベント）|
| 自動レビュー対象 | すべての PR（Draft PR を除く）|
| Copilot レビューの位置づけ | **補助的なファーストレビュー**として活用。Copilot のコメントはヒントとして扱い、人間レビュアーの承認を必須とする（ Required approvals と組み合わせる）|
| カスタマイズ（.github/copilot-instructions.md）| ＜例: コーディング規約・禁止パターン・特定の観点（セキュリティ/パフォーマンス等）を `copilot-instructions.md` に記載することで、プロジェクト固有のレビュー観点を追加できる＞ |

### 4.3. レビュー体制・マージ条件

| 項目 | 内容 |
|---|---|
| 必須レビュアー数 | ＜例: 1名以上（ のブランチ保護設定と整合）＞ |
| レビュアーのアサイン方法 | ＜例: 手動でアサイン / CODEOWNERS による自動アサイン＞ |
| ドラフト PR の扱い | ドラフト PR は作業中を示す。レビュー依頼前に「Ready for review」に変更してからレビュアーをアサインする |
| PR のサイズ目標 | 原則 **400行以下**（diff 行数）。大きな PR はレビュー品質が落ちるため、機能を分割して複数 PR にする |
| PR の放置期限 | 作成後 **＜例: 5営業日＞** 以内にマージまたはクローズする。期限超過の場合は毎日スタンドアップで確認する |
| マージ実行者 | ＜例: PR 作成者本人 / レビュアーによる承認後に PR 作成者がマージする＞ |

**マージ条件チェックリスト:**
- [ ] 必要な承認数を満たしている
- [ ] 全 CI ステータスチェックがグリーンである
- [ ] base ブランチと最新の状態で同期されている（up-to-date）
- [ ] 未解決の Conversation（レビューコメント）がない

## 5. CI 設計（継続的インテグレーション）

### 5.1. CI プラットフォームと実行環境

| 項目 | 内容 |
|---|---|
| CI プラットフォーム | ＜例: GitHub Actions＞ |
| ランナー | ＜例: `ubuntu-latest`（GitHub ホスト型ランナー）＞ |
| ワークフローファイル配置 | `.github/workflows/` 配下 |

### 5.2. CI ジョブ一覧

| ジョブ名 | トリガー | 内容 | ブランチ保護との連動 |
|---|---|---|---|
| `lint` | PR 作成・更新 | コードスタイル違反の検出（Checkstyle / ESLint 等）| 必須ステータスチェック |
| `unit-test` | PR 作成・更新 | ユニットテストの実行・カバレッジレポート生成 | 必須ステータスチェック |
| `build` | PR 作成・更新 | アプリケーションのビルド（WAR / JAR ファイル生成）| 必須ステータスチェック |
| `sast-scan` | PR 作成・更新 | 静的セキュリティ解析（CodeQL / Trivy 等）| 必須ステータスチェック |
| `dependency-check` | PR 作成・更新 / 週次定期実行 | 依存ライブラリの脆弱性スキャン（Dependabot / OWASP Dependency-Check）| PR 時は任意（定期実行で管理）|
| `integration-test` | `develop` / `main` へのマージ後 | 統合テストの実行（DBを含む結合テスト）| デプロイ前の品質確認（ブランチ保護とは別）|
| `deploy-dev` | `develop` へのマージ後 | 開発環境へのデプロイ（§6 参照）| — |
| `deploy-prod` | `main` へのマージ後（手動承認要）| 本番環境へのデプロイ（§6 参照）| — |

### 5.3. ジョブ詳細定義

#### `lint` — コードスタイル検査

| 項目 | 内容 |
|---|---|
| トリガー | `pull_request`（`main` / `develop` へのPR）|
| ツール | ＜例: Checkstyle（Java）。設定ファイル: `checkstyle.xml`＞ |
| 失敗時の挙動 | ワークフロー失敗 → PR マージがブロックされる |
| 除外対象 | 自動生成コード（`/generated/` 配下等）は除外する |

#### `unit-test` — ユニットテスト

| 項目 | 内容 |
|---|---|
| トリガー | `pull_request` |
| テストフレームワーク | ＜例: JUnit 5 / Mockito＞ |
| カバレッジ計測 | ＜例: JaCoCo（レポートを GitHub Actions Artifacts にアップロード）＞ |
| カバレッジ目標 | ＜例: ライン カバレッジ 70% 以上（目標値。未達でも CI は失敗させない）＞ |
| 失敗時の挙動 | テスト失敗時はワークフロー失敗 → PR マージがブロックされる |

#### `build` — ビルド検証

| 項目 | 内容 |
|---|---|
| トリガー | `pull_request` |
| ビルドツール | ＜例: Gradle / Maven＞ |
| ビルド成果物 | ＜例: WAR ファイル（`app.war`）＞ |
| 成果物の保存 | PR 時: GitHub Actions Artifacts に保存（7日間保持）。デプロイ時: リリースタグのアーティファクトとして保存 |

#### `sast-scan` — 静的セキュリティ解析

| 項目 | 内容 |
|---|---|
| トリガー | `pull_request` / `push to main`（週次定期実行も可）|
| ツール | ＜例: CodeQL（GitHub Advanced Security）＞ |
| 解析対象言語 | ＜例: Java / JavaScript＞ |
| 重大度フィルタ | Critical / High の脆弱性を検出した場合は CI を失敗させる |
| 失敗時の挙動 | Critical / High 検出時はワークフロー失敗 → PR マージがブロックされる |

> **TODO:** CodeQL は GitHub Advanced Security が必要（プライベートリポジトリは有料）。無料の代替として Trivy（コンテナ・IaC スキャン）や Semgrep（SAST）の利用を検討すること。

## 6. CD 設計（継続的デリバリー）

### 6.1. デプロイ対象環境

| 環境名 | 対応ブランチ | 基盤 | デプロイトリガー | 承認要件 |
|---|---|---|---|---|
| 開発環境 | `develop` | ＜例: ＜クラウドプラットフォーム＞ ＜プラン名＞＞ | `develop` へのマージ後・自動デプロイ | 不要 |
| ステージング環境 | `release/*` / `main`（pre-prod）| ＜例: ＜クラウドプラットフォーム＞ ＜プラン名＞（本番相当設定）＞ | 手動トリガー（環境保護ルール）| ＜例: リードエンジニア承認＞ |
| 本番環境 | `main` | ＜例: ＜クラウドプラットフォーム＞ ＜プラン名＞＞ | 手動トリガー（環境保護ルール）| ＜例: PL 承認 + リードエンジニア承認＞ |

### 6.2. ＜クラウドプラットフォーム＞ へのデプロイ方式

＜クラウドプラットフォーム＞ 環境へのデプロイは、**管理コンソールの「デプロイ機能」機能**（）を使って実施する。
GitHub Actions から直接 SSH 等で APサーバにアクセスすることはできない（AMP の制約）。

**デプロイ手順:**

1. GitHub Actions でアプリケーションをビルドし WAR ファイルを生成する
2. GitHub Actions から ＜クラウドプラットフォーム＞ の SFTP エンドポイントへ WAR ファイルをアップロードする（＜SFTP 利用可否は AMP サポートへ確認が必要＞）
3. 管理コンソール「デプロイ機能」機能からデプロイを実行する（＜または: ＜クラウドプラットフォーム＞ API が提供されている場合は API 経由で自動化する＞）

### 6.3. デプロイパイプライン（開発環境）

```
[develop ブランチへのマージ]
        ↓
[GitHub Actions: CI ジョブ実行（lint + unit-test + build + sast-scan）]
        ↓（全ジョブ成功時のみ）
[GitHub Actions: integration-test（DB含む統合テスト）]
        ↓（成功時のみ）
[GitHub Actions: deploy-dev（開発環境へ自動デプロイ）]
        ↓
[デプロイ完了通知（Slack / メール）]
        ↓
[自動スモークテスト（簡易ヘルスチェック確認）]
```

### 6.4. デプロイパイプライン（本番環境）

```
[main ブランチへのマージ（PR 承認 + CI グリーンが前提）]
        ↓
[GitHub Actions: CI ジョブ再実行（lint + unit-test + build + sast-scan）]
        ↓（全ジョブ成功時のみ）
[GitHub Actions: 本番デプロイワークフロー（環境保護ルールによる承認待ち）]
        ↓（PL + リードエンジニア承認後）
[デプロイ前バックアップ取得（AMP 管理コンソール: ）]
        ↓
[GitHub Actions: deploy-prod（本番環境へデプロイ）]
        ↓
[デプロイ完了通知（Slack / メール）]
        ↓
[自動スモークテスト / 外形監視確認（基盤概要設計_監視編 §2.2 参照）]
        ↓（スモークテスト異常時はロールバック手順へ: §9）
```

### 6.5. GitHub Environments 設定

GitHub の `Settings > Environments` で以下の環境保護ルールを設定する。

| 環境名 | 承認者 | Wait timer | Deployment branches |
|---|---|---|---|
| `development` | なし（自動デプロイ）| なし | `develop` のみ |
| `staging` | ＜例: リードエンジニア＞ | なし | `release/*` / `main` |
| `production` | ＜例: PL + リードエンジニア（全員の承認が必要）＞ | ＜例: 10分（デプロイ開始を遅延させ取り消し可能にする）＞ | `main` のみ |

### 6.6. デプロイ通知設計

| イベント | 通知先 | 通知内容 |
|---|---|---|
| デプロイ開始 | ＜例: Slack #deploy チャンネル＞ | 環境・バージョン・実行者・開始時刻 |
| デプロイ成功 | ＜例: Slack #deploy チャンネル＞ | 環境・バージョン・完了時刻・スモークテスト結果 |
| デプロイ失敗 | ＜例: Slack #deploy チャンネル + 担当者 DM＞ | 環境・エラー内容・ロールバック要否の確認 |
| 承認待ち（本番）| ＜例: 承認者への Slack DM + GitHub 通知＞ | 承認 URL・デプロイ内容の要約 |

## 7. バージョン・リリース管理

### 7.1. バージョン付け規則

＜例: **セマンティックバージョニング（SemVer）** を採用する。`MAJOR.MINOR.PATCH` の形式を使用する。＞

| バージョン要素 | 更新条件 | 例 |
|---|---|---|
| MAJOR | 後方互換性のない変更（外部 API の破壊的変更等）| `1.0.0` → `2.0.0` |
| MINOR | 後方互換性のある機能追加 | `1.0.0` → `1.1.0` |
| PATCH | 後方互換性のあるバグ修正 | `1.0.0` → `1.0.1` |
| ホットフィックス | 本番緊急修正（PATCH と同義）| `1.0.0` → `1.0.1` |

> **TODO:** セマンティックバージョニングが不適切な場合（例: 定期リリース型）は `YYYY.MM.DD` 形式（カレンダーバージョニング）の採用も検討すること。

### 7.2. タグ付け規則

| 項目 | 内容 |
|---|---|
| タグ形式 | `v{MAJOR}.{MINOR}.{PATCH}`（例: `v1.2.3`）|
| タグ付けタイミング | 本番デプロイ完了後に `main` ブランチの HEAD に付与する |
| タグ付け実行者 | ＜例: GitHub Actions（CD ワークフロー内で自動付与）/ リードエンジニアが手動付与＞ |
| タグのアノテーション | 軽量タグ（lightweight）ではなく、注釈付きタグ（annotated）を使用する |
| タグの保護 | GitHub の `Settings > Tags > Protected tags` で `v*` パターンを保護し、一般メンバーによるタグの削除を禁止する |

### 7.3. GitHub Releases

| 項目 | 内容 |
|---|---|
| Releases 作成タイミング | 本番デプロイ後にバージョンタグに対して GitHub Releases を作成する |
| リリースノートの内容 | ＜例: conventional commits または CHANGELOG.md をもとに自動生成（GitHub の「Auto-generate release notes」機能を使用）＞ |
| 添付アーティファクト | ビルド成果物（WAR ファイル等）を Releases に添付する |

### 7.4. CHANGELOG 管理

| 項目 | 内容 |
|---|---|
| 管理場所 | リポジトリルートの `CHANGELOG.md` |
| 記述形式 | ＜例: [Keep a Changelog](https://keepachangelog.com/) 形式＞ |
| 更新タイミング | リリースタグ付け時に更新する |
| 更新方法 | ＜例: 手動更新 / `git-cliff` / GitHub Actions による自動生成＞ |

## 8. 環境別設定・シークレット管理

### 8.1. 環境別設定の管理方針

| 項目 | 内容 |
|---|---|
| 設定ファイルの管理 | 環境共通の設定ファイルをリポジトリで管理し、環境固有の値は環境変数 / GitHub Secrets で注入する |
| `.env` ファイルの扱い | ローカル開発用の `.env` ファイルは **必ず `.gitignore` に追加**し、リポジトリにコミットしない |
| `.env.example` の管理 | 機密情報を含まないサンプル `.env.example` をリポジトリで管理し、開発者のローカル環境セットアップガイドとして活用する |
| 設定のカテゴリ分類 | 非機密設定（ログレベル・タイムゾーン等）: リポジトリで管理可。機密設定（パスワード・API キー等）: GitHub Secrets または Secrets Manager で管理 |

### 8.2. シークレット一覧

GitHub の `Settings > Secrets and variables > Actions` および各 `Environment` に以下を登録する。

| シークレット名 | 用途 | 対象環境 | 管理者 | ローテーション周期 |
|---|---|---|---|---|
| `DB_PASSWORD` | DBパスワード | development / staging / production（環境別）| ＜例: リードエンジニア＞ | ＜例: 半年ごと＞ |
| `SFTP_PRIVATE_KEY` | AMP SFTP 接続用秘密鍵 | development / production | ＜例: インフラ担当＞ | ＜例: 年1回＞ |
| `SLACK_WEBHOOK_URL` | デプロイ通知 Slack Webhook | 全環境共通 | ＜例: リードエンジニア＞ | ＜例: 失効時＞ |
| ＜追加シークレット名＞ | ＜用途＞ | ＜対象環境＞ | ＜管理者＞ | ＜周期＞ |

> **TODO:** 利用する外部サービスの API キーをシークレット一覧に追加すること。

### 8.3. シークレット漏洩防止策

| 対策 | 内容 |
|---|---|
| GitHub Secret Scanning | GitHub の Secret Scanning（`Settings > Code security > Secret scanning`）を有効化し、コミットにシークレットが含まれる場合にアラートを出す |
| pre-commit フック | ＜例: `detect-secrets` / `git-secrets` を pre-commit フックとして設定し、コミット前にシークレットを検出する＞ |
| `.gitignore` の管理 | `.env`・`*.pem`・`*.key`・`*.p12`・`credentials.*` 等のパターンをプロジェクト `.gitignore` に必須登録する |
| ワークフローログのマスク | GitHub Actions はシークレット値をログに出力しないが、`echo $SECRET` 等のデバッグコードをコミットしない |

## 9. 緊急リリース・ロールバック設計

### 9.1. ホットフィックス手順

本番環境で重大なバグが発生した場合の緊急リリース手順を以下に定義する。

```
[本番バグ検知（監視アラート / ユーザー報告）]
        ↓
[影響範囲・緊急度を判断（PL + リードエンジニア）]
        ↓（ホットフィックス対応を決定）
[main ブランチから hotfix/{issue}-{概要} ブランチを作成]
        ↓
[修正実装 + ユニットテスト追加]
        ↓
[PR 作成（hotfix → main）]
        ↓
[レビュー（人数: ＜例: 1名以上。緊急時は PL 判断で省略可・省略時は事後レビュー必須＞）]
        ↓（CI グリーン確認後）
[デプロイ前バックアップ取得（AMP 管理コンソール）]
        ↓
[本番環境へデプロイ（§6.4 本番デプロイパイプライン）]
        ↓
[スモークテスト・外形監視で修正適用を確認]
        ↓
[develop ブランチへもマージ（バックポート）]
        ↓
[インシデントレポート作成（根本原因・対策・再発防止策）]
```

**緊急時のレビュー省略条件:**

| 条件 | レビュー省略の可否 |
|---|---|
| 本番サービスが完全停止しており、即時修正なしには復旧できない | PL 判断で省略可（ただし事後に必ずレビューを実施）|
| データ損失・セキュリティ侵害が発生または進行中 | 同上 |
| それ以外の重大バグ | 省略不可（最低1名のレビュアーを確保する）|

### 9.2. ロールバック判断基準

デプロイ後、以下のいずれかの条件に該当した場合はロールバックを実施する。

| 判断基準 | 確認方法 | 担当者 |
|---|---|---|
| デプロイ後の外形監視で HTTP 5xx エラー率が 5% を超過 | 外形監視ツールのアラート（基盤概要設計_監視編 §4.1） | 運用担当 → リードエンジニア |
| デプロイ後のスモークテストが失敗 | GitHub Actions スモークテストジョブ | 自動検知 → 運用担当 |
| 重大な機能障害の報告（申請処理不可等） | ユーザー報告 / カスタマーサポート | リードエンジニア → PL |
| データ不整合が発生・拡大している | DB クエリによる確認 | リードエンジニア |

**ロールバック判断の権限:**

| ロールバック種別 | 判断者 | 所要時間目安 |
|---|---|---|
| 自動ロールバック（スモークテスト失敗）| 自動（人手不要）| ＜例: 5分以内＞ |
| 手動ロールバック（運用担当判断）| 運用担当（リードエンジニア承認）| ＜例: 15分以内＞ |
| 手動ロールバック（PL 判断）| PL | ＜例: 30分以内＞ |

> **注意:** ＜クラウドプラットフォーム＞ のデプロイはデプロイ機能（）を使用するため、ロールバックは「旧バージョンの WAR ファイルを再デプロイ」することで実現する。AMP によるインフラレベルのロールバック機能は提供されていない。

### 9.3. ロールバック手順

#### 前提: ロールバック前の確認事項

- [ ] デプロイ前に取得したバックアップの確認（AMP 管理コンソール「バックアップ」）
- [ ] ロールバック対象バージョン（旧バージョンの WAR ファイル）の特定（GitHub Releases から取得）
- [ ] DB スキーマ変更の有無の確認（変更がある場合はデータ移行スクリプトの逆適用が必要）

#### ロールバック実施手順

```
[ロールバック決定（担当者・承認者の合意）]
        ↓
1. デプロイメンテナンスモードを有効化（AMP 管理コンソール「メンテナンスモード ON」）
        ↓
2. 旧バージョンの WAR ファイルを GitHub Releases から取得
        ↓
3. AMP SFTP またはファイル操作機能で WAR ファイルをアップロード
        ↓
4. AMP 管理コンソール「デプロイ機能」で旧バージョンをデプロイ
        ↓
5. DBスキーマ変更がある場合: 逆適用マイグレーションスクリプトを実行
        ↓
6. メンテナンスモードを無効化
        ↓
7. 外形監視・スモークテストで正常復旧を確認
        ↓
8. ステークホルダーへの報告（影響時間・原因・対応内容）
        ↓
9. インシデントレポート作成（翌営業日まで）
```

> **TODO:** DB スキーマ変更（マイグレーション）のロールバック手順（逆適用スクリプトの管理方針）を DB 設計フェーズで確定すること。マイグレーションツール（Flyway / Liquibase 等）の採用有無と整合させること。

### 9.4. デプロイ後の検証手順

本番デプロイ完了後、以下の順序で正常稼働を確認する。

| # | 確認項目 | 確認方法 | OK 基準 | 確認担当 |
|---|---|---|---|---|
| 1 | URL 疎通確認 | 外形監視ツール / ブラウザ直接確認 | トップページが正常表示される | 運用担当 |
| 2 | ヘルスチェックエンドポイント応答 | `curl https://＜URL＞/health` | HTTP 200・`{"status":"ok"}` 相当 | GitHub Actions（自動スモークテスト）|
| 3 | 主要機能の疎通確認 | 手動操作（ログイン・申請参照・申請登録）| エラーなく処理が完了する | 運用担当 |
| 4 | エラーログの確認 | SFTP でログをダウンロード / AMP 管理コンソールでログ確認 | ERROR レベルのログが新規発生していない | 運用担当 |
| 5 | リソース利用率の確認 | AMP 管理コンソール「リソース表示」（）| CPU / メモリが通常範囲内（§性能・拡張性編 §6.1）| 運用担当 |
