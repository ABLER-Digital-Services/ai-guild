# 基盤概要設計_リリース管理編スキル

ソフトウェアの変更を安全・迅速・再現可能にリリースするための設計を定義するドキュメントを作成・更新する。
ブランチ戦略・ブランチ保護・PR レビュー・CI/CD パイプライン・バージョン管理・シークレット管理・緊急対応を
「コードが生まれる（ブランチ）→ 変更が審査される（PR/CI）→ 環境に届く（CD）→ 追跡可能になる（バージョン）→ 問題時に戻れる（ロールバック）」
の流れで一気通貫に設計し、開発チーム全体が迷わず運用できるリリーステンプレートを規定する。

## When to Use This Skill

- 「リリース管理設計書を作って」「基盤概要設計_リリース管理編を作って」と言われたとき
- 「ブランチ戦略を定義して」「Git 運用ルールを決めて」「ブランチ命名規則を整理して」と言われたとき
- 「直接 push を禁止して」「ブランチ保護ルールを設定して」「force push を禁止して」と言われたとき
- 「PR テンプレートを作って」「コードレビュー体制を定義して」「マージ条件を決めて」と言われたとき
- 「Copilot のコードレビューを設定して」「AI レビューを組み込んで」と言われたとき
- 「CI を設計して」「自動テストを組み込んで」「Lint・SAST を設定して」と言われたとき
- 「CD を設計して」「デプロイパイプラインを作って」「自動デプロイを設計して」と言われたとき
- 「セマンティックバージョニングを定義して」「タグ付け規則を決めて」「CHANGELOG を管理して」と言われたとき

## MECE 章構成の設計思想

リリース管理設計を「なぜ（方針）→ コードをどう管理するか（構成管理）→ どうレビューするか（品質保証）→ どう自動検証するか（CI）→ どうデプロイするか（CD）→ バージョンをどう識別するか（リリース管理）→ 環境差異をどう扱うか（設定管理）→ いざというときどうするか（緊急対応）」の流れで分解することで MECE を実現する。

```
1. 設計方針・適用範囲              ← なぜこの設計か、基本原則（Why）
2. ブランチ戦略                    ← コードをどう分岐・統合するか（Branch/Git 戦略）
3. ブランチ保護・アクセス管理       ← 誰が何を操作できるか（Protection/RBAC）
4. Pull Request・コードレビュー設計 ← 変更をどう審査・承認するか（PR/Review）
5. CI 設計（継続的インテグレーション）← 変更をどう自動検証するか（CI/Build/Test）
6. CD 設計（継続的デリバリー）      ← 検証済みコードをどう環境に届けるか（CD/Deploy）
7. バージョン・リリース管理         ← リリースをどう識別・追跡するか（Versioning/Tag）
8. 環境別設定・シークレット管理      ← 環境差異・機密情報をどう管理するか（Config/Secret）
9. 緊急リリース・ロールバック設計    ← 問題発生時にどう対処するか（Hotfix/Rollback）
```

**MECE の根拠:**
- 2（ブランチ戦略）≠ 3（ブランチ保護）: ブランチの「設計・命名」と「アクセス制御・保護設定」は独立した作業
- 3（保護設定）≠ 4（PR/レビュー）: 「誰が操作できるか」と「どうレビューするか」は別の関心事
- 4（PR/レビュー）≠ 5（CI）: レビューは「人の目による品質確認」、CI は「自動化された機械的検証」
- 5（CI）≠ 6（CD）: CI は「変更が正しいかの検証」、CD は「検証済みの変更を環境に反映する手順」
- 6（CD）≠ 7（バージョン管理）: CD は「デプロイの実行方法」、バージョン管理は「何をリリースしたかの記録」
- 7（バージョン管理）≠ 8（設定管理）: バージョン管理は「コードの識別」、設定管理は「環境依存値・機密情報の扱い」
- 8（設定管理）≠ 9（緊急対応）: 設定管理は「通常運用時の管理方法」、緊急対応は「異常発生時の対処手順」

## 作成ワークフロー

### Step 1: テンプレートをコピーして成果物を作成

例として、`templates/基盤概要設計_リリース管理編_template.md` を
`docs/01_要件定義/02_非機能/14_リリース管理/基盤概要設計_リリース管理編.md` にコピーして作業を開始する。

既存ファイルがある場合は上書きせず、差分を確認してから追記・修正する。

### Step 2: 関連ドキュメントの参照

以下のドキュメントを事前に参照し、設計の一貫性を確保する：

| ドキュメント | 参照目的 |
|---|---|
| `01_非機能要求グレード.md` | 運用・保守性要件（デプロイ頻度・リリース方式・ロールバック要件）の確認 |
| `基盤概要設計_サーバ編.md` | デプロイ対象サーバ（APサーバ）の構成とデプロイ手段の確認 |
| `基盤概要設計_クラウドサービス編.md` | 利用インフラのデプロイ方式制約の確認 |
| `基盤概要設計_セキュリティ編.md` | シークレット管理・アクセス制御設計との整合確認 |
| `基盤概要設計_監視編.md` | デプロイ後の死活監視・アラートとの整合確認 |
| `基盤概要設計_バックアップ・リカバリ編.md` | ロールバック時のデータリカバリ手順との整合確認 |
| `基盤概要設計_可用性編.md` | デプロイ方式（ゼロダウンタイム要否）との整合確認 |

### Step 3: ユーザーへのヒアリング

以下の観点でシステムの要件を確認する：

**ブランチ戦略の確認**
- Git ホスティングサービス（GitHub / GitLab / Bitbucket 等）
- 採用するブランチ戦略（GitHub Flow / Git Flow / Trunk-based Development 等）
- 長期ブランチの種別と役割（main / develop / release 等）
- マージ方式（Squash Merge / Rebase / Merge Commit）の方針

**ブランチ保護・アクセス管理の確認**
- 直接 push を禁止するブランチ（main のみか / develop も含めるか）
- 必須レビュアー人数（1名以上 / 2名以上）
- ステータスチェック（CI 成功必須か）の要否
- Dismiss stale reviews（新コミット後にレビュー承認を無効化する）の要否
- 管理者権限者への保護ルール適用の要否

**PR・コードレビューの確認**
- PR テンプレートの項目（概要・動作確認方法・チェックリスト等）
- GitHub Copilot コードレビューの有効化の要否
- レビュアー自動アサイン（CODEOWNERS / Auto-assign）の要否
- ドラフト PR の運用ルール
- WIP（作業中）PR の扱い

**CI の確認**
- CI プラットフォーム（GitHub Actions / CircleCI / Jenkins 等）
- 実行する CI ジョブ（テスト / Lint / ビルド / SAST / 依存関係脆弱性スキャン等）
- CI のトリガー（PR 作成時 / push 時 / 定期実行等）
- テストの種別と CI への組み込み範囲（ユニット / 統合 / E2E）
- CI 実行環境のセキュリティ要件（テナントの分離等）

**CD・デプロイの確認**
- デプロイ対象環境（開発 / ステージング / 本番）と昇格フロー
- 本番デプロイの承認フロー（誰が承認するか）
- デプロイ方式（マネージドサービスの機能デプロイか / GitHub Actions からの自動デプロイか）
- ゼロダウンタイムデプロイの要否（可用性編の方針と整合）
- デプロイ通知先（Slack / メール等）
- デプロイ後の自動スモークテストの要否

**バージョン・リリース管理の確認**
- バージョニング方式（セマンティックバージョニング / 日付ベース等）
- タグ付けのトリガー（手動 / 自動）
- CHANGELOG の管理方法（手動 / conventional commits からの自動生成）
- GitHub Releases の作成ルール

**シークレット管理の確認**
- 利用するシークレット管理手段（GitHub Secrets / AWS Secrets Manager / Vault 等）
- 環境別のシークレット分離方針（GitHub Environments 等）
- ローカル開発時の `.env` ファイルの管理方針（`.gitignore` 必須・git-crypt 等）
- シークレットのローテーション方針

**緊急リリース・ロールバックの確認**
- ホットフィックスのブランチ作成元（main から切るか）
- 緊急リリース時のレビュー省略可否と代替手続き
- ロールバック判断基準（誰がいつ判断するか）
- デプロイ前後のスナップショット・バックアップタイミング
- 旧バージョンへの切り戻し手順（利用プラットフォームのロールバック機能の有無）

### Step 4: 各セクションの記述

テンプレートのプレースホルダーをヒアリング結果に基づいて埋める。

記述の基本スタイル:
- ブランチ保護設定は「設定項目・値・理由」を表形式で整理する
- CI/CD パイプラインはジョブの「トリガー → ステップ → 成果物」の流れで記述する
- デプロイフローは環境ごとの昇格条件と承認者を明確にする
- シークレットは「シークレット名・用途・管理者・ローテーション周期」を一覧化する
- 未確定・要調査項目は `> **TODO:**` でマーク

記述例（ブランチ戦略）:

```markdown
| ブランチ種別 | 命名規則 | 分岐元 | マージ先 | 残存期間 |
|---|---|---|---|---|
| main | `main` | — | — | 永続 |
| develop | `develop` | `main` | `main`（PR 経由）| 永続 |
| 機能開発 | `feature/{issue番号}-{概要}` | `develop` | `develop`（PR 経由）| 機能完成まで |
| バグ修正 | `fix/{issue番号}-{概要}` | `develop` | `develop`（PR 経由）| 修正完成まで |
| ホットフィックス | `hotfix/{issue番号}-{概要}` | `main` | `main` ＆ `develop`（PR 経由）| 修正完成まで |
```

記述例（CI ジョブ定義）:

```markdown
### ジョブ: lint-and-test

| 項目 | 内容 |
|---|---|
| トリガー | PR 作成・更新時（`pull_request` イベント）|
| ランナー | `ubuntu-latest`（GitHub Actions）|
| ステップ | 1. Checkout → 2. Java セットアップ → 3. Lint（Checkstyle）→ 4. ユニットテスト（JUnit）→ 5. カバレッジレポート生成 |
| 成功条件 | 全テスト通過・Lint エラーなし |
| 失敗時の挙動 | PR マージをブロック（ブランチ保護のステータスチェックと連動）|
```

### Step 5: レビューチェック

- [ ] 採用するブランチ戦略が明示されており、ブランチ種別・命名規則・マージ方式が定義されているか
- [ ] 本番環境に対応するブランチ（main 等）への直接 push が禁止されているか
- [ ] 必須レビュアー数・ステータスチェック要件がブランチ保護ルールとして定義されているか
- [ ] force push が main / develop の永続ブランチで禁止されているか
- [ ] PR テンプレートの項目（概要・動作確認・チェックリスト）が定義されているか
- [ ] GitHub Copilot コードレビューの有効化方針が記載されているか
- [ ] CI でテスト・Lint・セキュリティスキャンが自動実行されるか定義されているか
- [ ] CI のトリガー・成功条件・マージブロック条件が明確か
- [ ] CD のデプロイ対象環境と昇格条件（誰の承認が必要か）が定義されているか
- [ ] マネージドサービス等のデプロイ制約（手動操作が必要な手順）が記載されているか
- [ ] セマンティックバージョニング等のバージョン付け規則が定義されているか
- [ ] シークレット（API キー・DB パスワード等）が VCS にコミットされない方針が明記されているか
- [ ] ホットフィックスの手順とレビュー省略条件が定義されているか
- [ ] ロールバックの判断基準と切り戻し手順が記載されているか
- [ ] デプロイ前後のバックアップ取得タイミングがバックアップ・リカバリ編と整合しているか
