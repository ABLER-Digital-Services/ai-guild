本書は「＜システム名＞」のバックアップ・リカバリ設計を定義する。
システムを構成するすべてのデータ・リソースのバックアップ取得方式・保管方針・リストア手順・障害復旧シナリオを規定し、
RTO/RPO 目標を達成するリカバリ体制を実現する。

## 前提条件

| 項目 | 内容 |
|---|---|
| 基盤 | ＜クラウドプラットフォーム・プラン名＞ |
| クラウドリージョン | ＜AWS リージョン（例: ap-northeast-1 東京）＞ |
| バックアップ管理責任 | ＜EBS/RDS/S3 はベンダー管理 / お客様管理 等＞ |
| 参照ドキュメント | ＜サービス仕様書・RFP 等＞ |
| 準拠法令・ガイドライン | ＜個人情報保護法 / 犯収法（7年）/ PCI DSS / 金融庁ガイドライン 等＞ |

### 管理責任区分

| 区分 | 意味 |
|---|---|
| **基盤管理** | クラウドプラットフォーム提供事業者（ベンダー）が管理・実施する |
| **お客様管理** | お客様（開発者・運用担当者）が設定・運用する |
| **お客様申請** | プラットフォーム事業者へ申請することで実施できる |

### バックアップ設計における基本方針

- **全対象カバレッジ原則**: システムを構成するすべてのデータ・設定ファイルを バックアップ対象一覧で棚卸しし、バックアップ漏れを発生させない
- **RTO/RPO 目標の優先**: 各データ種別の RTO/RPO 目標値に基づいてバックアップ頻度・保管期間・リストア手順を設計する
- **保管期間の根拠明示**: 各バックアップの保管期間は法令要件または運用要件を根拠として明記する
- **暗号化の徹底**: バックアップデータは保管中・転送中ともに AWS KMS（CMK）を使用して暗号化する
- **検証の実施**: バックアップの正常性はリストアテストによって定期的に確認する

## 3. 対象別バックアップ設計

### 3.1. RDS（データベース）

**概要**: アプリケーションのデータを格納する RDS のバックアップ設計。自動スナップショットによる日次フルバックアップと PITR（ポイントインタイムリカバリ）を組み合わせて RPO を最小化する。

| 項目 | 設定値 | 管理責任 |
|---|---|---|
| バックアップ方式 | 自動スナップショット（フル）+ PITR | ＜基盤管理 / お客様管理＞ |
| バックアップツール | ＜RDS 自動バックアップ / AWS Backup＞ | — |
| バックアップウィンドウ | ＜例: 02:00–03:00 JST（毎日）＞ | ＜基盤管理 / お客様設定＞ |
| PITR 有効化 | ＜有効 / 無効＞ | ＜基盤管理 / お客様設定＞ |
| PITR 保持期間 | ＜例: 7日間＞ | ＜基盤管理 / お客様設定＞ |
| 日次スナップショット保持期間 | ＜例: 30日＞ | ＜基盤管理 / お客様設定＞ |
| 月次スナップショット保持期間 | ＜例: 1年（手動スナップショット）＞ | ＜お客様管理＞ |
| 保管先 | S3（RDS 管理・AWS Backup 管理バケット） | ＜基盤管理＞ |
| 暗号化 | ＜AWS KMS（CMK）/ AWS マネージドキー＞ | ＜基盤管理 / お客様管理＞ |
| クロスリージョンコピー | ＜有効（DR対応）/ 無効＞ | ＜お客様管理＞ |
| マルチ AZ 構成 | ＜有効 / 無効（同期レプリカが別 AZ に常時存在）＞ | ＜基盤管理＞ |
| アプリ整合性 | RDS 自動スナップショットは DB をフリーズして整合性を保証 | — |

### 3.2. EBS ボリューム

**概要**: APサーバ・Storageサーバにアタッチされた EBS ボリュームのスナップショットバックアップ。AWS Backup または ベンダー のバックアップ機能を使用する。

| ボリューム | バックアップツール | 頻度 | 世代数 | 保持期間 | 管理責任 |
|---|---|---|---|---|---|
| APサーバ ルートボリューム | ＜AWS Backup / ベンダーバックアップ機能＞ | 1回/日 | ＜例: 14世代＞ | ＜例: 14日＞ | ＜基盤管理＞ |
| APサーバ アプリケーションボリューム | ＜AWS Backup / ベンダーバックアップ機能＞ | 1回/日 | ＜例: 14世代＞ | ＜例: 14日＞ | ＜基盤管理＞ |
| Storageサーバ ストレージボリューム | ＜AWS Backup / ベンダーバックアップ機能＞ | 1回/日 | ＜例: 14世代＞ | ＜例: 14日＞ | ＜基盤管理＞ |
| Storageサーバ セッション管理ボリューム | ＜AWS Backup / ベンダーバックアップ機能＞ | 1回/日 | ＜例: 14世代＞ | ＜例: 14日＞ | ＜基盤管理＞ |

**EBS バックアップの共通方針:**
- バックアップタイミング: ＜例: アプリケーション停止メンテナンス中 / オンライン中（クラッシュ整合）＞
- スナップショット方式: ＜増分スナップショット（前回スナップショット差分のみ転送）＞
- 暗号化: ＜AWS KMS（CMK）でソースボリュームと同じキーを使用＞

### 3.3. S3 バケット

**概要**: アプリケーションが利用する S3 バケット（ユーザーアップロードファイル・システム生成ファイル等）のバックアップ設計。

| バケット名 | 用途 | バックアップ方式 | バージョニング | クロスリージョンレプリケーション | 保持期間 |
|---|---|---|---|---|---|
| ＜バケット名＞ | ＜ユーザーアップロード等＞ | ＜バージョニング＞ | ＜有効＞ | ＜有効（DR対応）/ 無効＞ | ＜例: 旧バージョン 90日＞ |

**S3 バックアップの共通方針:**
- バージョニング: ＜有効化（誤削除・誤上書きからの保護）＞
- MFA Delete: ＜有効（重要データの誤削除防止）/ 無効＞
- Object Lock: ＜有効（WORM 保護）/ 無効＞
- 暗号化: ＜SSE-S3 / SSE-KMS（CMK）＞
- ライフサイクルポリシー: ＜旧バージョンを ○○ 日後に削除 / Glacier に移行＞

## 5. リストア設計

### 5.1. リストア実施フロー（概要）

```
障害検知
  │
  ▼
① 障害内容の特定（データ損失範囲 / 対象サーバ・DB の確認）
  │
  ▼
② 利用可能な最新バックアップの確認
  │
  ├── RDS スナップショット / PITR の確認
  ├── EBS スナップショット の確認
  └── S3 バージョン履歴 / バックアップの確認
  │
  ▼
③ リストア実施（対象別の手順に従う）
  │
  ▼
④ リストア後の動作確認
  │
  ▼
⑤ サービス再開・事後報告
```

## 6. DR（障害復旧）設計

### 6.1. 対応する障害シナリオ

| # | 障害シナリオ | 影響範囲 | 対応方針 | RTO | RPO |
|---|---|---|---|---|---|
| DR-01 | AZ 障害（単一 AZ 停止） | APサーバ / RDS プライマリ | マルチ AZ フェイルオーバー / EBS スナップショットから別 AZ で再構築 | ＜例: 1〜2時間＞ | ＜例: 0〜数分（マルチAZフェイルオーバー）＞ |
| DR-02 | リージョン障害（東京リージョン停止） | システム全体 | クロスリージョンスナップショットから大阪リージョンで再構築 | ＜例: 8〜12時間＞ | ＜例: 24時間＞ |
| DR-03 | データ誤削除（オペレーションミス） | 対象テーブル / ファイル | PITR / S3 バージョニングで復元 | ＜例: 1〜2時間＞ | ＜例: 発生時刻の直前まで（PITR）＞ |
| DR-04 | ランサムウェア・データ暗号化 | 対象ストレージ全体 | S3 Object Lock（WORM）/ クロスリージョンバックアップから復元 | ＜例: 8〜24時間＞ | ＜例: 感染前の最新バックアップ時点＞ |
| DR-05 | 論理破壊（DB データ破損・不整合） | 対象 DB テーブル | PITR / スナップショットから復元 + データ整合性確認 | ＜例: 2〜4時間＞ | ＜例: 破損前の時点（PITR）＞ |

### 6.2. AZ 障害時の復旧フロー（DR-01）

```
AZ 障害検知（CloudWatch Alarm / 監視アラート）
  │
  ▼
① RDS: マルチ AZ 構成であれば自動フェイルオーバー（数分で完了）
② APサーバ: 別 AZ でインスタンスを再起動（ベンダー の場合はサポートへ連絡）
  │
  ▼
アプリケーション接続先変更（DNS フェイルオーバー / 手動更新）
  │
  ▼
動作確認 → サービス再開
```

### 8.3. コスト最適化方針

- **S3 ライフサイクルポリシー**: アクセス頻度が低いバックアップは S3 Standard-IA → Glacier へのライフサイクル移行でコストを削減する
- **増分スナップショット**: EBS スナップショットは増分方式のため、初回以降のスナップショットサイズを抑える
- **保管期間の最適化**: 法令要件を超える必要以上に長い保管期間は設定しない
- **不要バックアップの整理**: テスト時に手動取得したスナップショットは期限を設定して自動削除する
