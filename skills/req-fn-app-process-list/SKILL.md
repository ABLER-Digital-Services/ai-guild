# 処理一覧スキル

画面上のボタン・リンク・フォーム送信などをトリガーとして起動される**サーバサイド処理**を一覧化する。
バッチ処理・JavaScriptのみで完結するクライアントサイドイベントは対象外とする。

## When to Use This Skill

- 「処理一覧を作って」「サーバ処理を整理して」と言われたとき
- API設計・バックエンド実装の前提整理として
- 既存の処理一覧をレビュー・更新するとき

## 成果物の仕様


## 対象・対象外の判断基準

| 区分 | 対象 | 対象外 |
|---|---|---|
| **オンライン** | ボタン・リンク押下によりサーバへリクエストが飛ぶ処理 | JavaScriptのみで完結するUI操作（入力バリデーション表示、アコーディオン展開など） |
| **バッチ** | ― | すべて対象外（機能一覧のバッチ機能で管理） |

## 処理ID採番ルール

| フォーマット | 例 |
|---|---|
| `P-NNN` | `P-001`、`P-002` |

- NNNは3桁ゼロ埋め
- 遷移前機能ID（画面）の順番に沿って採番する
- 一度採番したIDは欠番になっても振り直さない

## 作成ワークフロー

### Step 1: 機能一覧の確認

機能一覧（`04_機能一覧/01_機能一覧.md`）のオンライン機能セクションを参照し、対象画面を把握する。

### Step 2: 各画面の処理洗い出し（ヒアリング）

各オンライン機能（画面）について以下を確認する：

1. **ボタン・リンクの種類**: 登録・更新・削除・検索・送信・ダウンロードなど
2. **処理後の遷移先**: 同画面リロード・別画面へ遷移・モーダル表示など
3. **処理の概要**: サーバ側で何をするか（DB登録・外部API呼び出し・ファイル生成など）
4. **対象アクター**: その処理を実行できるアクター（アクター定義書を参照）

### Step 3: ドキュメント生成

`templates/process-list-template.md` を元にドキュメントを生成する。

以下のルールを守ること：
- `遷移前機能ID` / `遷移後機能ID` は機能一覧の `F-O-NNN` を使う
- 遷移後が同じ画面（リロード・エラー表示）の場合は遷移前と同じIDを記載する
- 遷移後が存在しない場合（ダウンロード・非同期APIなど）は「－」とする
- 概要は「何をする処理か」を体言止めで記載する

### Step 4: レビューチェック

- [ ] 機能一覧のオンライン機能すべてのボタン・リンクが網羅されているか
- [ ] JavaScriptのみの処理が混入していないか
- [ ] 機能IDが機能一覧の `F-O-NNN` と一致しているか
- [ ] アクター名がアクター定義書と一致しているか
- [ ] 処理IDの採番形式（`P-NNN`）が守られているか
