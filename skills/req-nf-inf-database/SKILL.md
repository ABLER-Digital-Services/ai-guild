# データベース設計書スキル

システムのデータベース構成（DBエンジン選定・インスタンス設計・接続設計・スキーマ設計方針・バックアップ・パフォーマンス・セキュリティ等）を定義するドキュメントを作成・更新する。
「データをどこに・どう格納し・どう守るか」を軸に設計要素を MECE に分解し、段階的に詳細化するドキュメント構成を採用する。

## When to Use This Skill

- 「データベース設計書を作って」「基盤概要設計_データベース編を作って」と言われたとき
- 「DB設計を整理して」「DBエンジンを選定して」と言われたとき
- 「接続設計を書いて」「コネクションプールを設計して」と言われたとき
- 「スキーマ設計方針を定義して」「テーブル設計ルールを整理して」と言われたとき
- 「DBバックアップを設計して」「DBのパフォーマンス方針を書いて」と言われたとき
- 既存のデータベース設計書をレビュー・更新するとき

## MECE章構成の設計思想

データベース設計を「データをどこに・どう扱うか」の構成要素に分解することで MECE を実現する。

```
1. 設計方針・前提条件       ← なぜこの設計か、誰が管理するか（Why/Who）
2. DBエンジン選定           ← どのDBを使うか（Engine）
3. インスタンス設計          ← どのスペックで動かすか（Compute/Capacity）
4. 接続設計                ← どこからどう繋ぐか（Connectivity）
5. スキーマ設計方針         ← データをどう構造化するか（Structure）
6. テーブル設計方針         ← テーブル・インデックスをどう設計するか（Table Design）
7. バックアップ・リカバリ設計 ← データをどう守るか（Protection）
8. パフォーマンス・拡張性設計 ← 性能をどう確保するか（Performance）
9. セキュリティ設計         ← 不正アクセスをどう防ぐか（Security）
10. メンテナンス方針        ← 継続的にどう運用するか（Operation）
```

**MECEの根拠**:
- 2（何を使うか）≠ 3（どのスペックか）: エンジン選定は種別・バージョンの決定、インスタンスはリソースの決定
- 4（どう繋ぐか）≠ 9（どう守るか）: 接続設計は経路・プロトコル、セキュリティは認証・暗号化・権限という別軸
- 5（構造化）≠ 6（テーブル設計）: スキーマ方針は命名規則・文字コード等の規約、テーブル設計はPK/インデックス等の実装方針
- 7（バックアップ）≠ 8（パフォーマンス）: 保護観点 vs. 性能観点

## 作成ワークフロー

### Step 1: テンプレートをコピーして成果物を作成

例として、`templates/基盤概要設計_データベース編_template.md` を
`docs/01_要件定義/02_非機能/07_データベース/基盤概要設計_データベース編.md` にコピーして作業を開始する。

既存ファイルがある場合は上書きせず、差分を確認してから追記・修正する。

### Step 2: 関連ドキュメントを参照して前提を把握する

以下のドキュメントが存在する場合は先に参照し、データベース設計の前提を確認する：

| 参照先 | 確認ポイント |
|---|---|
| `02_システム構成/01_システム構成図.md` | 全体アーキテクチャ・DBの位置づけ・外部システム連携 |
| `03_クラウドサービス/基盤概要設計_クラウドサービス編.md` | 利用AWSサービス（RDS等）・インスタンスタイプ・管理責任範囲 |
| `04_サーバ/基盤概要設計_サーバ編.md` | DBサーバのスペック（CPU・メモリ・ディスク）・接続元サーバ構成 |
| `05_ストレージ/基盤概要設計_ストレージ編.md` | RDSストレージ設計・バックアップ設計との整合 |
| `01_非機能要求グレード/01_非機能要求グレード.md` | 可用性・性能・セキュリティ・データ保管期間に関する要件 |
| `08_セキュリティ/基盤概要設計_セキュリティ編.md` | 暗号化要件・アクセス制御方針との整合 |

**マネージドサービスを利用する場合の補足**:
マネージドサービスを利用する場合、RDS インスタンスの設定（インスタンスタイプ・パラメータグループ・マルチAZ等）は
ベンダーが管理するため、お客様（開発者）が設定できる項目は限られる。
各章で「ベンダー管理（設定不可）」と「お客様設定可」を明示して記述する。

| 設計要素 | 管理責任 | お客様の操作 |
|---|---|---|
| RDS インスタンスタイプ / ストレージサイズ | **ベンダー管理** | プラン変更申込のみ可 |
| DBエンジン / バージョン | **ベンダー管理** | 申込時にエンジン種別を選択可（開通後は変更不可） |
| パラメータグループ（DB設定値） | **ベンダー管理** | 変更不可（カスタムパラメータは申込で対応） |
| マルチAZ / リードレプリカ | **ベンダー管理** | 設定不可 |
| DBバックアップ（スナップショット） | **ベンダー提供** | スケジュール・世代数はお客様が運用管理サイトで設定可 |
| DBアカウント（アプリ用ユーザー） | **お客様管理** | DDL/DMLの権限をアプリ側で設計・管理 |
| スキーマ・テーブル設計 | **お客様管理** | 完全にお客様が設計・実装 |

### Step 3: ユーザーへのヒアリング

#### 1. 設計方針・前提条件
- システム名・データベースの役割（基幹DB / セッションDB / ログDB 等）
- 利用するプラットフォーム（クラウドマネージド RDS / セルフマネージ RDS / Aurora 等）
- 環境数（本番 / ステージング / 開発）と各環境のDB設計方針の差異

#### 2. DBエンジン選定
- 採用するDBエンジン種別（PostgreSQL / MySQL / Oracle / SQL Server / Aurora 等）
- バージョン選定の根拠（ESサポート期間・アプリフレームワーク対応・クライアント互換性）
- 文字セット（UTF-8 / UTF-8MB4 等）・照合順序（ci / cs・Unicodeノーマライズ方針）

#### 3. インスタンス設計
- vCPU 数・メモリサイズ（クラウドの場合はインスタンスタイプ）
- ストレージ容量・種別（SSD / HDD / Io1 等）・IOPS
- マルチAZ（冗長化）の要否
- スケールアップ方針（プラン変更 / インスタンスクラス変更のタイミング）

#### 4. 接続設計
- 接続元サービス（APサーバ / バッチサーバ / 管理ツール 等）
- 接続プロトコル・ポート番号（PostgreSQL: 5432 / MySQL: 3306 等）
- 最大接続数（max_connections）とコネクションプールの設定方針
- コネクションプールミドルウェアの有無（PgBouncer / HikariCP 等）
- 接続元 IP 制限（VPC 内のみか・外部ツールからの接続要否）

#### 5. スキーマ設計方針
- スキーマ（データベース）分割方針（機能別 / テナント別 等）
- テーブル名・カラム名の命名規則（スネークケース / キャメルケース 等）
- 予約語・プレフィックス・サフィックス規則
- NULL 許容方針（原則 NOT NULL か / NULLを許容する条件）
- デフォルト値設定方針（created_at / updated_at 等の自動設定）

#### 6. テーブル設計方針
- 主キー（PK）の設計方針（サロゲートキー / 自然キー / UUID / シーケンス）
- ユニークキー（UK）の設計方針
- 外部キー（FK）制約の使用方針（アプリ管理 vs. DB制約）
- インデックス設計方針（検索性能を重視する列・複合インデックス方針）
- 物理削除 vs. 論理削除方針
- 大量データテーブルのパーティショニング要否

#### 7. バックアップ・リカバリ設計
- バックアップ方式（スナップショット / ダンプ / PITR 等）
- バックアップスケジュール（日次 / 週次 / 月次）と保管世代数
- 保管期間の要件
- リストア手順・RTO（目標復旧時間）/ RPO（目標復旧時点）
- リストア単位（全体 / スキーマ単位 / テーブル単位 / 特定レコード）

#### 8. パフォーマンス・拡張性設計
- 同時接続数・クエリ数の見積もり（ピーク時）
- スロークエリ閾値・監視方針
- クエリチューニング方針（EXPLAIN 解析・インデックス最適化チェックタイミング）
- 読み取り負荷分散の要否（リードレプリカ 等）
- データ増加率の見積もりと容量増設計画

#### 9. セキュリティ設計
- DBアカウント管理方針（アプリ用 / DBA用 / 読み取り専用 等のロール分離）
- 最小権限原則の適用（SELECT のみ / DML まで / DDL まで）
- 保存データの暗号化（DB 側 / ストレージ側 / カラム単位）
- 通信暗号化（SSL/TLS 接続の強制）
- 監査ログ（pgaudit / MySQL General Log 等）の設定方針
- パスワードポリシー・定期ローテーション方針

#### 10. メンテナンス方針
- DBエンジン / OS パッチ適用の責任範囲と頻度
- メンテナンスウィンドウの設定（時間帯・影響範囲）
- 統計情報更新・VACUUM（PostgreSQL）/ ANALYZE 実行方針
- DDL 変更（マイグレーション）手順と方針（Blue/Green / 無停止 / 停止要 等）

### Step 4: 各セクションへの記述

ヒアリング結果をもとに、以下のフォーマットで各セクションを記述する。

```markdown
## ＜セクション名＞

**設計方針**
- ＜この設計を選択した理由・前提条件＞

**設計内容**
- ＜具体的な設定値・定義内容＞

**管理責任区分**
- ＜ベンダー管理（設定不可）か、お客様管理か＞

> **TODO:** 未確定事項を記述
```

- マネージドサービスを利用する場合は「お客様が設定できる項目」と「ベンダー管理の項目」を区別して記載する
- 設定値の根拠（非機能要求グレードの要件番号等）を明記する
- 未確定事項は `> **TODO:**` で明示する

### Step 5: レビューチェック

- [ ] DBエンジン・バージョンが決定しているか（`> **TODO:**` が残っていないか）
- [ ] インスタンス設計がクラウドサービス設計書（`03_クラウドサービス/`）・サーバ設計書（`04_サーバ/`）のスペック定義と一致しているか
- [ ] 接続設計の最大接続数がAPサーバのコネクションプール設定と整合しているか
- [ ] スキーマ設計方針（命名規則・NULL許容・PK方針）が記述されているか
- [ ] バックアップ設計の保管期間が非機能要求グレード（`01_非機能要求グレード/`）の要件と整合しているか
- [ ] バックアップ設計がストレージ設計書（`05_ストレージ/`）のRDSストレージ設計と一致しているか
- [ ] セキュリティ設計がセキュリティ要件定義書（`08_セキュリティ/`）と整合しているか
- [ ] マネージドサービスを利用する場合、ベンダー管理とお客様管理の責任分界が各セクションで明示されているか
- [ ] メンテナンスウィンドウがシステム運用要件と整合しているか

## テンプレートの構成

テンプレート（`templates/基盤概要設計_データベース編_template.md`）は以下のセクションで構成される：

| セクション | 内容 |
|---|---|
| 設計方針・前提条件 | 採用プラットフォーム・環境構成・管理責任区分の概要 |
| DBエンジン選定 | エンジン種別・バージョン・文字セット・照合順序 |
| インスタンス設計 | vCPU・メモリ・ストレージ・冗長化・スケールアップ方針（本番／開発） |
| 接続設計 | 接続元・プロトコル・ポート・最大接続数・コネクションプール |
| スキーマ設計方針 | スキーマ分割・命名規則・NULL許容・デフォルト値方針 |
| テーブル設計方針 | PK/UK/FK・インデックス・論理削除・パーティション方針 |
| バックアップ・リカバリ設計 | バックアップ方式・スケジュール・保管期間・リストア手順 |
| パフォーマンス・拡張性設計 | 接続数見積もり・スロークエリ閾値・チューニング方針・容量計画 |
| セキュリティ設計 | DBアカウント管理・最小権限・暗号化・監査ログ |
| メンテナンス方針 | パッチ適用・メンテナンスウィンドウ・統計情報更新・DDL変更手順 |
