# アクター定義書スキル

システムに関わるすべてのアクター（利用者・外部システム）を定義し、認可（アクセス制御）設計の土台となるドキュメントを作成する。

## When to Use This Skill

- 「アクター定義書を作って」と言われたとき
- 「ユーザー種別・ロール・権限を整理して」と言われたとき
- 業務フローや機能一覧を作る前の前提整理として
- 既存のアクター定義書をレビュー・更新するとき

## 作成ワークフロー

### Step 1: アクターの洗い出し（ヒアリング）

ユーザーに以下を確認する：

1. **人間アクター**: システムに直接ログイン・操作するユーザーは何種類いるか
2. **外部システムアクター**: API連携・バッチ連携する外部システムはあるか
3. **組織階層**: 管理者／一般利用者のような階層関係はあるか
4. **マルチテナント**: 複数の組織・企業をまたぐ構成か（例：SaaS）

### Step 2: 各アクターの詳細定義

各アクターについて以下を定義する：

- **役割の説明**: 誰が・どんな業務で使うか
- **できること（許可）**: 主要な操作・参照できる情報
- **できないこと（禁止）**: 明示的に制限される操作
- **認証方法**: ID/PW・SSO・APIキーなど
- **利用環境**: PC・モバイル・バックエンドなど

### Step 3: ドキュメント生成

`templates/actor-definition-template.md` を元にドキュメントを生成する。

以下のルールを守ること：
- アクター名はシステム全体で統一する固有名詞として定義する
- 漠然とした名称（「ユーザー」「管理者」）は避け、業務文脈を反映した名称にする
  - 悪い例: `ユーザー`　→　良い例: `一般会員`、`店舗スタッフ`
- 1アクター = テーブル1行ではなく、アクターごとのセクション（`###`）で詳細を記述する

### Step 4: レビューチェック

- [ ] すべての人間アクターが網羅されているか
- [ ] 外部システムアクターが漏れていないか
- [ ] アクター名がシステム全体で使う名称として適切か（業務文脈に即しているか）
- [ ] 「できること／できないこと」が具体的に記載されているか（曖昧な記載になっていないか）
- [ ] 認証方法が記載されているか
- [ ] アクター間の階層・包含関係が整理されているか

## 認可設計との連携

このドキュメントは以下の後続成果物の土台となる：

- **機能一覧** (`04_機能一覧.md`) — 各機能の「対象アクター」列に本書のアクター名を使う
- **画面遷移図** (`08_画面遷移図.md`) — アクター別の遷移パターンを定義する際に参照
- **インタフェース一覧** (`06_インタフェース一覧.md`) — 外部システムアクターの接続仕様に対応
