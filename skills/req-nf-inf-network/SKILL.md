# ネットワーク設計書スキル

システムのネットワーク構成（VPC・サブネット・ルーティング・アクセス制御・エッジ・外部接続等）を定義するドキュメントを作成・更新する。
「接続性（どう繋ぐか）」を軸に設計要素を MECE に分解し、段階的に詳細化するドキュメント構成を採用する。

## When to Use This Skill

- 「ネットワーク設計書を作って」「基盤概要設計_ネットワーク編を作って」と言われたとき
- 「ネットワークを整理して」「VPC設計を書いて」「サブネット設計を定義して」と言われたとき
- 「セキュリティグループを定義して」「NAT ゲートウェイの設計を書いて」と言われたとき
- 「外部接続を整理して」「VPCピアリングを定義して」「WAF設計を書いて」と言われたとき
- 既存のネットワーク設計書をレビュー・更新するとき

## MECE章構成の設計思想

ネットワーク設計を「データが通る道」の構成要素に分解することで MECE を実現する。
各章は「何を定義するか」という観点で重複がなく、段階的に詳細化される。

```
1. 設計方針・前提条件     ← なぜこの設計か、誰が管理するか（Why/Who）
2. ネットワーク全体構成   ← どんなゾーンに分けるか（Big Picture）
3. VPC・サブネット設計    ← どこに何を置くか（Space/配置）
4. ルーティング設計       ← どこへどう繋ぐか（Connectivity/経路）
5. アクセス制御設計       ← 誰をどこへ通すか（Filtering/フィルタ）
6. エッジ設計            ← 外から内へどう届くか（Entry Point/入口）
7. 外部接続設計          ← 外部と双方向でどう繋ぐか（External/外部系統）
8. 帯域・データ転送設計   ← どれだけの容量が必要か（Capacity/容量）
9. 監視・ログ設計        ← どう観察するか（Observability/可観測性）
```

**MECEの根拠**:
- 3（どこに置くか）≠ 4（どう繋ぐか）: サブネットはアドレス空間の定義、ルーティングは経路の定義
- 4（どう繋ぐか）≠ 5（誰を通すか）: ルーティングは「経路の存在」、アクセス制御は「通過の可否」
- 5（誰を通すか）≠ 6（外からどう届くか）: SG/NACLは通過ルール、ALB/CFはエントリーポイント定義
- 6（外からの受信）≠ 7（外部との相互接続）: 単方向受信（公開） vs 双方向特定接続（VPN/Peering）

## 作成ワークフロー

### Step 1: テンプレートをコピーして成果物を作成

例として、`templates/基盤概要設計_ネットワーク編_template.md` を
`docs/01_要件定義/02_非機能/06_ネットワーク/基盤概要設計_ネットワーク編.md` にコピーして作業を開始する。

既存ファイルがある場合は上書きせず、差分を確認してから追記・修正する。

### Step 2: 関連ドキュメントを参照して前提を把握する

以下のドキュメントが存在する場合は先に参照し、ネットワーク設計の前提を確認する：

| 参照先 | 確認ポイント |
|---|---|
| `02_システム構成/01_システム構成図.md` | 全体アーキテクチャ・サーバ配置・外部システム連携 |
| `03_クラウドサービス/基盤概要設計_クラウドサービス編.md` | 利用AWSサービス（VPC・EC2・RDS・ALB・CloudFront等）一覧 |
| `04_サーバ/基盤概要設計_サーバ編.md` | 各サーバのNIC構成・IPアドレス |
| `01_非機能要求グレード/01_非機能要求グレード.md` | セキュリティ要件・可用性要件・外部接続要件 |
| `08_セキュリティ/基盤概要設計_セキュリティ編.md` | セキュリティグループポリシー・WAFルール方針 |

**マネージドサービスを利用する場合の補足**:
マネージドサービスを利用する場合、VPC・サブネット・ルートテーブル・IGW・NAT GW などの設定はベンダー管理となる場合があるため、
各章で「ベンダー管理（設定不可）」と「お客様設定可」を明示して記述する。
ベンダーの仕様書・契約内容を参照して、正確な設定可能範囲を事前に確認する。

### Step 3: ユーザーへのヒアリング

#### 設計方針
- セキュリティゾーニングの方針（Public/Private/Isolated の分離構成）
- 冗長化方針（マルチAZ構成の要否、単一AZ運用可否）
- 環境数と分離方式（本番・ステージング・開発を VPC で分けるか、サブネットで分けるか）
- 外部システムとのネットワーク接続要否（VPCピアリング・VPN・Direct Connect）

#### VPC・サブネット設計
- VPC CIDR ブロック（例: `10.0.0.0/16`）
- サブネット種別と CIDR（Public / Private / Database 等）
- アベイラビリティゾーン数（1AZ か マルチAZ か）
- 固定IPアドレスが必要なリソースの有無

#### ルーティング設計
- インターネット向け通信の有無（APサーバからの外部API呼び出し等）
- NAT ゲートウェイの配置 AZ 数（シングル AZ か マルチ AZ か）
- VPC プライベートエンドポイントが必要な AWS サービス（S3・Secrets Manager 等）

#### アクセス制御設計
- セキュリティグループの設計方針（最小権限／ゼロトラスト等）
- 運用担当者からの IP 制限要件（管理用途・ SFTP 等のアクセス元 IP 制限）
- WAF が必要なリソース（公開 Web サイト・API エンドポイント）

#### エッジ設計
- ロードバランサーが必要なリソースと種別（ALB / NLB）
- CDN（CloudFront）の要否と用途（静的コンテンツ配信・WAF オフロード等）
- DNS 設計（ドメイン名・Route 53 ホストゾーン・CNAMEレコード等）
- HTTPS 対応の要否（ACM 証明書の管理方針）

#### 外部接続設計
- VPC ピアリング要否（他の AWS アカウント・VPC との接続。例: お客様独自の S3 バケットへのアクセス）
- オンプレミスとの接続方式（VPN / Direct Connect）の要否
- AWS PrivateLink の要否（SaaS サービス等との接続）

#### 帯域・データ転送
- 想定ピーク時のスループット（内外通信）
- リージョン間・AZ間データ転送の見積もり

#### 監視・ログ
- VPC Flow Logs の有効化要否と保管先（CloudWatch Logs / S3）
- ネットワーク関連メトリクスのアラート設定方針

### Step 4: 各セクションへの記述

#### VPC・サブネット設計の記述フォーマット（汎用 AWS の場合）

```markdown
### VPC 設計

| 項目 | 本番 | 開発 |
|---|---|---|
| VPC 名 | ＜VPC名＞ | ＜VPC名＞ |
| CIDR ブロック | ＜CIDR＞ | ＜CIDR＞ |
| リージョン | ＜リージョン＞ | ＜リージョン＞ |
| AZ 数 | ＜AZ数＞ | ＜AZ数＞ |
| DNS hostname | 有効 | 有効 |
| DNS resolution | 有効 | 有効 |

### サブネット設計

| サブネット名 | 種別 | CIDR | AZ | 用途 |
|---|---|---|---|---|
| ＜サブネット名＞ | Public | ＜CIDR＞ | ap-northeast-1a | ALB・NAT GW 配置 |
| ＜サブネット名＞ | Private | ＜CIDR＞ | ap-northeast-1a | EC2（APサーバ）配置 |
| ＜サブネット名＞ | Isolated | ＜CIDR＞ | ap-northeast-1a | RDS 配置 |
```

#### セキュリティグループの記述フォーマット

```markdown
### ＜SG名＞（＜対象リソース＞用）

**インバウンドルール**

| ルール | プロトコル | ポート | 送信元 | 説明 |
|---|---|---|---|---|
| ＜ルール識別子＞ | TCP | 443 | 0.0.0.0/0 | HTTPS（インターネットからのアクセス） |
| ＜ルール識別子＞ | TCP | 80 | 0.0.0.0/0 | HTTP（HTTPS リダイレクト用） |

**アウトバウンドルール**

| ルール | プロトコル | ポート | 宛先 | 説明 |
|---|---|---|---|---|
| ＜ルール識別子＞ | All | All | 0.0.0.0/0 | すべての送信を許可（デフォルト） |
```

- AMP 管理の場合は「ベンダー基盤側で設定済み。お客様は変更不可」と明記する
- 未確定・要確認事項は `> **TODO:**` で明示する

#### マネージドサービス利用時の記述の注意点

ベンダーが管理する環境では、VPC・サブネットの CIDR はベンダーが提供する仕様書・契約内容に記載された情報をそのまま記録する形になる。
設定値の決定権はお客様にない点を明示する。

```markdown
### VPC 設計（ベンダー管理）

**管理責任**: ベンダー（マネージドサービス提供者）  
**お客様設定可否**: 設定不可

| 項目 | 内容 | 根拠 |
|---|---|---|
| VPC CIDR | ＜ベンダー仕様書の値＞ | サービス契約内容 |
| リージョン | ＜リージョン＞ | サービス仕様書 |
| AZ 構成 | ＜AZ数＞ AZ | サービス仕様書 |
```

### Step 5: レビューチェック

- [ ] 設計方針にセキュリティゾーニング方針・冗長化方針・責任分担が記述されているか
- [ ] VPC・サブネット設計の CIDR 設計に重複がなく、将来拡張の余地があるか
- [ ] ルートテーブルにPublic/Private/Isolated の各サブネットの経路が定義されているか
- [ ] NATゲートウェイの配置AZが冗長化要件を満たしているか（マルチAZが必要な場合）
- [ ] セキュリティグループがサービス間通信の最小権限で設計されているか
- [ ] 外部公開エンドポイント（ALB・CF）の前段に WAF が配置されているか（必要な場合）
- [ ] DNS レコード（ALB/CF の CNAME 等）と実際のリソース名が一致しているか
- [ ] 外部接続（VPCピアリング等）を使用する場合、対向CIDR との重複がないか
- [ ] VPC Flow Logs の有効化と保管先（CloudWatch / S3）が定義されているか
- [ ] クラウドサービス設計書（`03_クラウドサービス/`）に記載した VPC・SG リソースと一致しているか

## テンプレートの構成

テンプレート（`templates/基盤概要設計_ネットワーク編_template.md`）は以下のセクションで構成される：

| セクション | MECE上の役割 | 主な記述内容 |
|---|---|---|
| 設計方針・前提条件 | Why/Who（目的・責任） | セキュリティゾーニング方針・管理責任分担・命名規則 |
| ネットワーク全体構成 | Big Picture（全体観） | ゾーン設計・環境別構成・構成図への参照 |
| VPC・サブネット設計 | Space（配置） | VPC CIDR・サブネット種別・AZ 構成・IP割り当て表 |
| ルーティング設計 | Connectivity（経路） | ルートテーブル・IGW・NAT GW・VPC エンドポイント |
| アクセス制御設計 | Filtering（通過可否） | セキュリティグループ・NACL・WAF・IP 制限 |
| エッジ設計 | Entry Point（入口） | ALB/NLB・CloudFront・Route 53・ACM 証明書 |
| 外部接続設計 | External（外部系統） | VPCピアリング・VPN・Direct Connect・PrivateLink |
| 帯域・データ転送設計 | Capacity（容量） | 推定スループット・データ転送コスト見積もり |
| 監視・ログ設計 | Observability（可観測性） | VPC Flow Logs・CloudWatch メトリクス・アラート |
