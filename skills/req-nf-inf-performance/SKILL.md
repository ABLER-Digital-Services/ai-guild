# 基盤概要設計_性能・拡張性編スキル

システムが達成すべき性能目標（レスポンスタイム・スループット・リソース利用率）を定義し、
初期キャパシティ設計・将来の業務量増大に備えたスケールアップ計画・
アプリケーション層での性能最適化方針・性能監視設計・性能テスト計画を規定するドキュメントを作成・更新する。
非機能要求グレードの性能・拡張性要件から逆算し、「現時点で充足できるか」と
「将来の業務量増大にどう対応するか」の両面で設計を整理する。

## MECE 章構成の設計思想

性能・拡張性設計を「なぜ（目標）→ 何が（要件）→ どう（設計）→ 将来（計画）→ 検証」の流れで分解することで MECE を実現する。

```
1. 設計方針・性能目標          ← なぜこの設計か、性能目標・設計原則（Why）
2. 性能要件一覧               ← 何が要件か、数値で整理（What/棚卸し）
3. キャパシティ設計            ← 初期構成で充足できるか（How/コンピュート・DB・ストレージ）
4. スケールアップ・拡張計画     ← 将来業務量増大にどう対応するか（Scale）
5. アプリケーション性能設計     ← アプリ層での性能確保手段（App/キャッシュ・DB最適化）
6. 性能監視設計               ← 性能劣化をどう検知するか（Monitor）
7. 性能テスト設計              ← 性能目標達成をどう検証するか（Test）
```

**MECE の根拠:**
- 2（何が要件か）≠ 3（現構成で充足できるか）: 要件の列挙とキャパシティ充足評価は独立した作業
- 3（キャパシティ設計）≠ 4（スケールアップ計画）: 現時点の初期構成と将来の拡張方針は別の関心事
- 4（スケールアップ）≠ 5（アプリ性能設計）: インフラ層の拡張とアプリ層の最適化は異なる解決手段
- 5（アプリ性能設計）≠ 6（性能監視）: 性能を「確保する手段」と「劣化を検知する手段」は別の活動
- 6（性能監視）≠ 7（性能テスト）: 本番環境での常時監視と事前の性能検証テストは別の活動

## 作成ワークフロー

### Step 1: テンプレートをコピーして成果物を作成

例として、`templates/基盤概要設計_性能・拡張性編_template.md` を
`docs/01_要件定義/02_非機能/13_性能・拡張性/基盤概要設計_性能・拡張性編.md` にコピーして作業を開始する。

既存ファイルがある場合は上書きせず、差分を確認してから追記・修正する。

### Step 2: 関連ドキュメントの参照

以下のドキュメントを事前に参照し、設計の一貫性を確保する：

| ドキュメント | 参照目的 |
|---|---|
| `01_非機能要求グレード.md` | 性能目標（レスポンスタイム・同時アクセス数・ユーザ数増大率・CPU/メモリ利用率）の確認 |
| `基盤概要設計_クラウドサービス編.md` | 利用 AWS サービス・構成オプション確認 |
| `基盤概要設計_サーバ編.md` | APサーバのインスタンスタイプ・vCPU・メモリ容量・現行スペックの確認 |
| `基盤概要設計_データベース編.md` | RDS インスタンスタイプ・接続数上限・クエリ性能設計の確認 |
| `基盤概要設計_ストレージ編.md` | ストレージ容量・I/O 性能設計の確認 |
| `基盤概要設計_ネットワーク編.md` | 帯域幅・ALB 設定・ネットワーク性能の確認 |
| `基盤概要設計_監視編.md` | CPU/メモリ/レスポンス監視の設定との整合確認 |
| `基盤概要設計_可用性編.md` | スケーリング設計・Auto Scaling との整合確認 |

### Step 3: ユーザーへのヒアリング

以下の観点でシステムの要件を確認する：

**性能目標の確認**
- レスポンスタイム目標（通常時・ピーク時の上限値と順守率）
- スループット目標（同時アクセス数・オンラインリクエスト件数・バッチ処理件数）
- リソース利用率目標（CPU・メモリ・ストレージ・ネットワーク帯域の目標値）
- 性能目標の根拠（RFP・SLA・業界標準値等）

**キャパシティ要件の確認**
- 現行業務量（初期フェーズのアクセス数・データ量）
- ピーク時の多重度（平常時との倍率）
- バッチ処理のピーク時刻・処理件数・処理時間目標
- マネージドサービスを利用する場合のキャパシティ制約（スケールアウト不可などベンダー制約）

**拡張性要件の確認**
- 将来の業務量増大率（同時アクセス数・リクエスト件数の増大倍率）
- 拡張の手段・制約（スケールアップのみか / スケールアウトも可能か）
- インスタンスタイプ・プラン変更の申請手続きと所要時間
- コスト制約から許容できるスペックアップの上限

**アプリケーション性能の確認**
- キャッシュ利用の有無・対象データ（セッション・参照マスタ等）
- DB クエリの複雑度・インデックス設計の現状
- コネクションプール設定の有無・上限値
- 静的コンテンツの CDN 利用有無

**性能テストの確認**
- 負荷試験の実施有無・対象環境（本番相当か否か）
- 負荷試験のシナリオ（同時アクセス数・継続時間・操作内容）
- 性能テストの受入基準（何をもって「合格」とするか）
- 性能テスト実施タイミング（リリース前・定期実施等）

### Step 4: 各セクションの記述

テンプレートのプレースホルダーをヒアリング結果に基づいて埋める。

記述の基本スタイル:
- 性能目標値は必ず数値で明示し、根拠（RFP 条項・非機能要求グレード等）を付記する
- キャパシティ設計では「現行要件への充足評価」を必ず記載し、不足がある場合は対応方針を示す
- スケールアップ計画では「いつ・何をトリガーに・どのスペックへ」を具体的に定義する
- 未確定・要調査項目は `> **TODO:**` でマーク

記述例（キャパシティ設計）:

```markdown
### APサーバ（EC2）

| 項目 | 現行スペック | 充足評価 |
|---|---|---|
| vCPU | 4vCPU | △ 同時40件は充足見込み。ピーク時CPU 70%超過の浸念あり |
| メモリ | 16 GiB | ○ 8GiB余裕あり |
| 同時接続数 | インスタンス設定による | 要確認（最大同時接続数設定値の確認が必要）|

> **TODO:** APサーバの最大同時接続数設定値を確認すること。
```

記述例（スケールアップ計画）:

```markdown
| トリガー指標 | 閾値 | 対応アクション | 所要期間目安 |
|---|---|---|---|
| CPU利用率（ピーク時平均） | 10分間 70% 超過が 3日連続 | インスタンスタイプアップまたはプラン変更を申請 | 申請後の対応期間をベンダーに確認 |
| 月間リクエスト件数 | 800件/日 超過が継続 | 上位スペックへの変更を検討 | ベンダー対応期間による |
```

### Step 5: レビューチェック

- [ ] 性能目標（レスポンスタイム・スループット・CPU/メモリ利用率）が数値で明示されているか
- [ ] 非機能要求グレードの性能・拡張性要件と整合しているか
- [ ] 初期キャパシティが現行業務量を充足できるか評価されているか
- [ ] 充足できない項目に対する対応方針が記載されているか
- [ ] 将来の業務量増大率（例: 5倍）に対応できるスケールアップ計画があるか
- [ ] スケールアップのトリガー指標・閾値・対応アクションが具体的か
- [ ] プラン変更・スペック変更に伴う停止リスクが明記されているか
- [ ] アプリケーション層での性能最適化方針（キャッシュ・クエリ最適化等）が定義されているか
- [ ] DB コネクションプールの上限が RDS 最大接続数と整合しているか
- [ ] 性能監視の指標・閾値・アラート設計が監視編と整合しているか
- [ ] 負荷試験計画（シナリオ・受入基準・実施タイミング）が定義されているか
- [ ] マネージドサービスを利用する場合、ベンダー制約（スケールアウト不可など）と整合しているか
- [ ] ピーク時と通常時で別々の性能目標・監視閾値が設定されているか

## テンプレートの構成

テンプレート（`templates/基盤概要設計_性能・拡張性編_template.md`）は以下のセクションで構成される：

| # | セクション | 主な内容 |
|---|---|---|
| 1 | 設計方針・性能目標 | 性能目標値（レスポンスタイム・スループット・リソース利用率）・設計原則・根拠 |
| 2 | 性能要件一覧 | ユーザ数・同時アクセス数・リクエスト件数・データ量・増大率をまとめた要件表 |
| 3 | キャパシティ設計 | コンピュート（APサーバ）・DB・ストレージ・ネットワーク帯域ごとの充足評価 |
| 4 | スケールアップ・拡張計画 | 拡張方針・スケールアップトリガー・プラン変更手続き・制約・将来キャパシティ試算 |
| 5 | アプリケーション性能設計 | キャッシュ方針・DBクエリ最適化・コネクションプール・静的コンテンツ配信 |
| 6 | 性能監視設計 | 監視指標・通常時／ピーク時閾値・アラート発報条件・エスカレーション |
| 7 | 性能テスト設計 | テスト種別・テストシナリオ・受入基準・実施環境・実施タイミング |
